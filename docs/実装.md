# お金と食事の記録アプリ — 実装の手順

最終更新: 2026-10-20

---

## この文書について

**作る順番と、各段階の「終わったと言える条件」を書いてある。**

前のアプリの失敗分析で「要件が未定義だった」ことが原因の1つに挙がり、その対策として**判定可能な条件の形で書く**と決めた。この文書でもそれに従い、各段階に**完了の条件**を置いてある。条件を満たしていなければ、その段階は終わっていない。

**1段階ずつ進める。** 完了の条件を満たしてから次へ行く。複数を並行して進めない。

**文書はリポジトリの `docs/` にある。** 2026-10-20 以降、そちらが正。

| 文書 | 役割 |
|---|---|
| 仕様.md | 何を作るか。作業の直前に該当箇所だけ読む |
| 判断の記録.md | なぜそうするか。迷ったとき引く |
| 進行状況.md | どこまで進んだか |
| **実装.md**（この文書） | **どの順で作るか。作業中はこれを開く** |

## この順番にした理由

### 核から作る

| 段階 | 性質 |
|---|---|
| 0〜2 | **土台。薄く端から端まで通すためのもの** |
| **3 その日の画面** | **核。毎日の記録そのもの** |
| 4〜8 | 肉付け |

段階0〜2は作り込みではなく、**公開までの道筋を通す**作業である。

「最初にごく薄い機能を端から端まで通し、公開までの道筋が機能していることを確かめる」という考え方（Walking Skeleton）に沿っている。価値が出るのは公開された状態だけなので、早い段階で出せる状態を確保しておく。

### 通知を最後にした理由

| 判断 | 内容 |
|---|---|
| #39・#46 | **通知は補助。開いた瞬間の画面が本体** |
| 結果 | **通知が動かなくてもアプリは成立する** |

通知が失敗しても、段階2〜7の作り方は何も変わらない。**早く知っても判断が変わらないので、早くやる価値がない。**

一方、通知を先にすると段階3（使い始められる地点）が後ろにずれ、10.3 の計測開始が遅れる。

**ただしリスクが1つ残る。** 失敗分析（2.4）で「通知がなく存在を忘れる」が原因の1つに挙がっている。段階3から段階8までの期間、通知なしで使うことになる。これは #39 で「開いた瞬間の画面を本体とする」と決めて織り込み済みであり、**その設計が正しかったかの検証にもなる。**

### ホーム画面への追加を段階1に置いた理由

通知の条件でもあるが、**それ以前に 14.6 で決めた「作る形」そのもの**である。アイコンから開けないと、4.3 の「利用頻度が高いこと」を満たす形にならない。通知とは別の要件なので、段階1に置く。

### ログインを段階2に置いた理由

**公開した瞬間、ログインがなければ誰でも記録を読み書きできる**（#57）。段階1では画面に文字が出るだけでデータを置かないため問題ないが、**データを置く段階2と同時に必要になる。**

後から入れると、既に入っている行に利用者を埋める作業が発生する。

# 段階2 データの土台 + ログイン

**目的:** 記録を保存でき、かつ**自分以外が触れない**状態にする。

### なぜログインを同時にやるのか

Webアプリは、データベースに繋ぐための鍵をブラウザの中に持つ。この鍵は公開される前提のもので、守っているのはデータベース側の行単位のアクセス制御である。

**その制御は「誰がアクセスしているか」を条件に書く。ログインがないと材料が存在しない。**

ログインなしで公開すると、URLを知っている人は誰でも記録を読めて、書き換えられて、消せる（#57）。

### やること

1. Supabase の Authentication で、自分のアカウントを1つ作る（管理画面から）
2. ログインの画面を作る（メールアドレスとパスワードのみ）
3. 4つの表を作る

```
記録の表     id / 利用者 / 日付 / 時刻 / 種類 / 金額 / 備考
食事の表     記録id / 枠 / 自炊か外食か
メニューの表  id / 記録id / メニュー名
送り先の表   id / 利用者 / 送り先 / 登録日時
```

4. **4つすべてに、行単位のアクセス制御を有効にする**
5. 「自分の行だけ読み書きできる」決まりを書く
6. アプリから1行書き込み、読み出せることを確かめる

### 完了の条件

- [ ] ログインしていない状態では、ログインの画面しか出ない
- [ ] 自分のアカウントでログインできる
- [ ] 4つの表が Supabase にある
- [ ] **4つすべてで、行単位のアクセス制御が有効になっている**
- [ ] **アプリから1行書き込める**
- [ ] 書き込んだ行が、アプリの画面に表示される
- [ ] **閉じて開き直しても、その行が残っている**
- [ ] **ログインしていない状態で表を読もうとすると、何も返ってこない**

### 読む箇所

仕様.md の **13.5**（表の形）と **7.9**（ログイン）。約6ページ。**実データの例まで読むこと。**

### 注意

**ここを後から変えると全部作り直しになる。** 13.5 の「各列を置いた理由」を読んでから作る。

**SQLで表を作ると、アクセス制御は最初オフのまま。** 自分で有効にする必要がある。有効にし忘れても画面は正常に動くので、気づけない。**完了の条件に入れてあるのはこのため。**

食事の表とメニューの表には利用者の列を置かない。記録idを辿れば誰のものか分かるため。

「その他」という種類は置かない（#34）。「日」の表は作らない（#35）。

### この段階の意味

**ここで薄く端から端まで通る。** 画面 → ログイン → 書き込み → 保存 → 読み出し → 画面、が1周する。以降はこの骨組みに肉を付けていく作業になる。

# 段階3 その日の画面 ← 核

**目的:** 毎日の記録ができる状態にする。**ここが終われば使い始められる。**

### やること

1日の枠を並べ、押したセルにその場で打つ形を作る。

```
10月13日(月)

 起床    7:05
 ──────────────────────────────────
  朝     8:12   自炊   目玉焼き、味噌汁
  昼    12:40   外食   ラーメン、餃子       ¥900
  晩    19:30   自炊   カレー
  間食    ―      ―      ―
 ──────────────────────────────────
 入眠   23:40

 買い物   スーパー                        ¥2,340
 この日の出費                             ¥3,240
```

### 完了の条件

- [ ] 起床・朝・昼・晩・間食・入眠の枠が並ぶ
- [ ] 自炊か外食かの欄を押すと、自炊 / 外食 / **なし** が選べる
- [ ] 時刻の欄を押すと、分単位で時刻を入れられる
- [ ] メニューの欄を押すと、文字が打てる。**1回の食事に複数入れられる**
- [ ] 買い物の金額を入れられる
- [ ] その日の出費の合計が出る
- [ ] **記録していない枠と「なし」が、見た目で区別できる**
- [ ] 備考を書ける（行の右端の印を押すと開く）
- [ ] 入れた記録を直せる・消せる
- [ ] **日付を変えて、過去の日にも入力できる**
- [ ] 閉じて開き直しても、記録が残っている

### 読む箇所

仕様.md の **7.5**（その日の画面）、**6.1**（1日の形）、**6.2**（共通の決まり）。約6ページ。

### 注意

**別の画面に移らない。** 下からせり上がる入力欄も出さない。押したセルにその場で打つ（#22）。

**「なし」は記録の一種である。** 空欄とは別物。ここを混ぜると段階4の記録日数が数えられなくなる。

**この段階が一番難しい。** 押した場所ごとに入力の形が変わるため、画面の状態の管理が細かくなる。

### ここが終わったら

**毎日使い始めること。** 10.3 の記録日数がここから数え始まる。段階4以降を作りながら、並行して記録する。

# 段階4 記録日数

**目的:** 続き具合が見えるようにする。

### やること

3つの数字を出す。

```
記録日数   累計   87日
          今月   24日 / 31日
          連続   12日（最高 24日）
```

### 完了の条件

- [ ] 累計・今月・連続（最高記録つき）の3つが出る
- [ ] 朝・昼・晩・間食の4つが埋まった日だけが数えられている
- [ ] 「なし」の枠も、埋まったものとして数えられている
- [ ] 買い物の有無は数に影響しない

### 読む箇所

仕様.md の **7.4**（記録日数の数え方）、**10.3**（目標）。約3ページ。

### 注意

**データに「完了した」という印を持たせない。** 記録から計算する（#10、#35）。

**連続日数には必ず最高記録を併記する。** 1日忘れた翌日に「連続 0日」とだけ出ると、積み上げが全部消えた感覚になる（#17）。

**マス目だけで見せない。数字をはっきり出す**（10.4）。

**目的:** 出費の変化に気づけるようにする。

### やること

**6-1. まず金額だけの表**

```
 9月   ¥16,756

```

**6-2. その後グラフに置き換える**

```
 出費の動向

 [ 日 ]  [ 週 ]  [ 月 ]

 ◀  2026年  ▶

        ┌──────────────┐
        │  9月    ¥16,756   ▶│
        └──────────────┘

  (万)
   2 ┤                █
   1 ┤   █ █ █   █ █  █  █
   0 └──────────────────
     1月 2月 3月 ... 9月 10月

 ──────────────────────
  この期間の記録を見る   →
```

### 完了の条件

**6-1**

- [ ] 期間ごとの食費の合計が並ぶ
- [ ] 日 / 週 / 月 を切り替えられる

**6-2**

- [ ] 棒グラフになっている

- [ ] 年を切り替えられる
- [ ] 日を選んだとき、その月の日数分の棒が並ぶ
- [ ] **平均は出さない**
- [ ] 「この期間の記録を見る」から、その期間を表示した状態で全記録画面に移動する

# 段階8 通知

**目的:** 毎晩、その日の記録の状況が届くようにする。

### 8-1 まず成立するか確かめる

本番を作る前に、**最小の実験**をする。14.3 に「iPhone でのWebアプリの通知は、最初は動くが、その後予期せず止まる場合があるという報告がある」と書いてある。**これは読んでも分からない。試すしかない。**

**やること**

1. 鍵のペア（VAPID鍵）を作る
2. ホーム画面のアイコンから開き、通知を許可する
3. 発行された送り先を画面に表示させる（まだ保存しない）
4. その送り先に向けて、手元から1通だけ送ってみる

**完了の条件**

- [ ] 通知の許可を求める表示が出る
- [ ] 許可すると、送り先の文字列が得られる
- [ ] **アプリを閉じた状態で、通知が1通届く**

**成立しなかった場合**

アプリ自体は成立する（#39）。選択肢は2つ。

| 案 | 内容 |
|---|---|
| ア | 通知を諦め、7.1 の機能を5つにする。開いた瞬間の画面だけで回す |
| イ | 別の手段を探す（メールで送るなど） |

**その場合、8-2 は作らない。** 他の段階は全て終わっているので、ここで止めてもアプリは完成している。

### 8-2 本番を作る

**やること**

1. 通知を許可したとき、送り先を表に保存する
2. Supabase で pg_cron を有効にする
3. Edge Function を作り、通知の文章を作って送る処理を書く
4. 毎晩21時に動くように設定する

**完了の条件**

- [ ] 通知を許可すると、送り先が表に保存される
- [ ] 同じ送り先が2回登録されても、行が増えない（登録日時だけ更新される）
- [ ] 毎晩21時に通知が届く
- [ ] 通知の中身が、その日の記録の状況になっている（どの枠が埋まっているか）
- [ ] 送信に失敗した送り先が、表から消える
- [ ] 通知を切ると、その行が消える

### 読む箇所

仕様.md の **13.8**（通知の送り先を保存する表）、**14.2**（通知の仕組み）。約4ページ。

### 注意

**Safari で普通に開いた状態では、通知の許可を求めることすらできない。** ホーム画面のアイコンから開くこと。

**通知は「入力を促す」ものではなく「その日の記録の状況を見せる」もの**（7.1）。

**登録されている送り先、全部に送る**（#53）。1件だけに絞らない。

送信する部分は `web-push` という既にある部品を使える。暗号の処理をゼロから書く必要はない。

## 行き詰まったときの判断

| 状況 | どうするか |
|---|---|
| ある段階に時間がかかりすぎている | **その段階の完了の条件を見直す。** 条件を減らして先に進め、減らした分を記録に残す |
| 仕様と違うものを作りたくなった | **判断の記録を引く。** その形を選ばなかった理由が書いてある。それでも変えるなら、新しい判断として記録に足す |
| 未決定のものにぶつかった | 進行状況.md の未決定一覧にあるか確認する。あれば、そこで決めて記録に足す |
| 7日記録が途切れた | Supabase のプロジェクトが止まっている可能性がある。管理画面から「Resume project」で再開する。**データは消えていない**（14.3） |
