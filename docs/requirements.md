# 第1部 なぜ作るのか

## 1. 前のアプリで何が起きたか

### 1.1 出発点

既存のリポジトリ `hiroppy-udon/my-task-app` を改善しようとしていたが、アプリの目的を見失った。

調べたところ、README に書かれた内容と、実際のコードの中身が食い違っていた。

| | README の記述 | コードの実態 |
|---|---|---|
| アプリの性質 | タスク管理 + モチベーション音声録音 | 目標に対する「誓約」アプリ |
| データ保存 | LocalStorage のみ | Supabase が正、LocalStorage は控え |
| 暗号化 | AES-GCM を `src/utils/crypto.ts` に実装中 | 該当するコードは存在しない |
| 構成 | `src/components/`、TailwindCSS | `src/App.jsx` 単体 + `src/lib/supabase.js`、素の CSS |
| 記載なし | — | `vite-plugin-pwa`、`react-calendar-heatmap` |

README をコードの実態に合わせて全面的に書き直し、Supabase の環境変数の記載を追加してコミット済み(`c5f8e9c..ee09ab5`)。

### 1.2 それでも残った問題

README のずれを直しても「使う気が起こらない」状態は変わらなかった。掘り下げた結果、次のことがわかった。

- my-task-app の目的は「録音によるモチベーション維持」だった
- 生活習慣を管理していた時期は使っていたが、その必要がなくなった
- 今管理したいのは **モチベーションではなく、お金や食事といった自然に発生するもの**

→ my-task-app を改造するのではなく、**用途の違う新しいプロダクト**として切り出す。my-task-app はそのまま残す。

## 2. 記録が続かなかった理由

因果の構造図を作り、「アプリへの記録が続かない」に至る道筋を分析した。

### 2.1 直接の原因(5つ)

1. 生活にこのアプリを使うという行動がない
2. 「その場でサッと記録する」ことへの心理的なハードルが上がる
3. 画面の使い勝手が悪かった
4. 使う頻度が低く、目に入れる機会がない
5. 怠惰(直りにくい)

### 2.2 大元の原因

**「プロダクトを早く完成させることにこだわった」** が、上の 2・3・4 の3つに波及していた。

```
インターン選考に間に合わないと思った
(実際はコードレビューやフレームワーク選定の根拠こそ求められると後で気づいた。しかも落ちた)
    ↓
ポートフォリオがないことに対する焦り
    ↓
プロダクトを早く完成させることにこだわった
    ├→ 音声アプリの要件が決まっていなかった
    │     → 解決したい課題がない、危機感がない
    │         ├→ 生活にこのアプリを使う行動がない
    │         └→ その場でサッと記録する心理的ハードル
    ├→ AIが書いたコードを見直さなかった
    │     → 画面の使い勝手が悪かった →【直接の原因へ】
    └→ アイコンが目立たない → 使う頻度が低い
```

### 2.3 直さないと決めたもの

| 原因 | 扱い | 理由 |
|---|---|---|
| アイコンが目立たない | 対象外 | 全体への影響が小さい |
| 怠惰(直りにくい) | **受け入れる** | 直すものではなく付き合うもの |
| ポートフォリオへの焦り | 解消済み | 年内という期日はあるが以前のような焦りはない。趣味として時間を割ける |

**「怠惰は直さない」という判断は、設計の考え方そのものを決める条件になった。**

→ 意志や心がけに頼る対策はすべて使えない。「サボらないようにする」のではなく「サボれない仕組みにする」。

### 2.4 直すと決めたものと、その打ち手

言い換えただけの対策(「要件が決まっていなかった」→「要件を決める」)にならないよう立てた。

| 原因 | 打ち手 |
|---|---|
| 作って終わり、使う姿を想像できなかった | 実装の前に、実際に使う場面を書き出す。完成の定義を「実装が終わった」ではなく「使い続けられた」に置く |
| 通知がなく存在を忘れる | 通知を最初から要件に入れる。ただし「入力を促す」のではなく「その日の記録の状況を見せる」形にする |
| 要件が決まっていなかった | 要件を機能の一覧ではなく、**後から達成できたか判定できる条件**の形で書く |
| 早く完成させることにこだわった | 焦りは解消済み。代わりに「学習」と「実用」を優先するものとして明示する |

## 3. 人から受けた指摘

### 3.1 データの設計について

AIで作った管理系の仕組みは、データの設計が破綻していて2〜3年で運用が崩壊するものが多い。データが溜まるほど読み出しが遅くなり、データ同士の関係も考えられていない。動かし始めだけは動くので気づかない。原因は、画面のことしか考えず、データの構造を理解しないままAIに指示を出していること。

**本件への適用:** 前回の失敗「AIのコードを見直さなかった → 使い勝手が悪かった」と同じことが、今回はデータの設計で起きうる。**AIが出した表の定義をそのまま使わない。なぜその形なのかを自分で説明できる状態にする。**

### 3.2 ポートフォリオの README について

書類選考ではコードは読まれない。見られるのは README の最初の1画面。入れるべきは次の4つ。

1. **課題** — 誰の何が困っていたのか(1〜2文)
2. **解き方** — 構成図を1枚
3. **結果** — 前と後の数字。指標の名前と、どう測ったかまで
4. **判断** — なぜその技術を選んだか。**選ばなかった候補も書く**

4つ目まで書いてある人はほとんどいない。ここがあると「動かした人」ではなく「決めた人」として読まれる。公開しているデモのリンク切れは最大の事故。

**本件への適用:** README は最後に書くものではなく、**要件を決める過程と設計の過程が、そのまま材料になる**。特に「結果」は前の数字を先に押さえる必要があり、「判断」は選んだ過程を記録しないと後から書けない。

# 第2部 何を作るのか

## 4. 目的

目的は3つの層に分かれている。混同しないこと。

### 4.1 一番の目的

**エンジニア職に応募するときのポートフォリオ。および、それを作る過程での学習。**

### 4.2 実際に解決したいこと(題材)

**お金と健康の管理。** やりたいことは次の3つ。

1. **今日の食事・出費を記録する**(ゆくゆくは睡眠時間、やることなど生活全般へ広げる)
2. **月ごと、あるいは一週間の記録を確認する**
3. **記録を振り返って生活習慣を見直し、リズムを整え、次の週に活かす**

確認したい内容は2つ。

- **無駄なく抑えられているか**(お金の面)
- **安定した食事がとれているか**(食事の面)

**記録した先にあるもの(重要):** 記録することが目的ではない。**週という単位で振り返り、次の週の行動を変える**という流れを回すことが目的。したがって振り返りの画面は「見て終わり」ではなく、次の週の判断材料になる形である必要がある。

### 4.3 満たすべき条件

**利用頻度が高いこと。**

前のアプリ(my-task-app)は使う頻度が低く、使われなくなった。自分がよく触るプロダクトは「刺激がある」か「利用頻度が高い」かのどちらかであり、このアプリは後者を目指す。記録するタイプのアプリは、触る機会が多いほど習慣の一部に溶け込む。

ただし**これは目的ではなく、4.1 と 4.2 を達成するために満たすべき条件**である。使われていないプロダクトでは、ポートフォリオに載せる成果の数字(第2部 10)が出せない。

### 4.4 なぜ既存のアプリでなく自分で作るのか

順序に注意すること。

```
ポートフォリオが必要
  → 題材を何にするか
  → 自分が実際に困っていて、かつ毎日発生するものがいい
  → 記録の課題(レシートアプリやスプレッドシートの使いにくさ)を選んだ
```

レシートアプリへの不満は、**アプリを作る理由ではなく、題材を選ぶときの基準**である。

したがって「既存の家計簿アプリを使えば済むのでは」という問いへの答えは、「既存アプリを使ってもポートフォリオにはならない」になる。実用面の課題を解決するだけなら、既存アプリで足りる。

## 5. 使う場面

```
1日の終わり、帰宅した後
  → 落ち着いている、両手が空いている
  → その日の食事と買い物をまとめて入力する
  → 1日1回の操作
```

**この場面から決まること**

| 項目 | どうなるか |
|---|---|
| 極端にタップ数を減らすこと | 不要。落ち着いた状況なので数十秒かけられる |
| 1日分をまとめて入力する画面 | 必要 |
| 過去に遡って入力するための専用の画面 | 不要。日付の欄が編集できれば足りる |
| 通知 | **重要度が高い**。1日1回の操作なので、1回逃すと1日分が丸ごと抜ける |

## 6. 記録する内容

### 6.1 1日の形 — 枠という考え方

**1日には決まった枠がある。並びはもともと決まっているので、時間順に並べ替える必要がない。**

```
起床 → 朝 → 昼 → 晩 → 間食 → 入眠
```

この並びがそのまま1日の形になる。毎日同じ形で固定する。

**枠ごとに記録する内容**

| 枠 | 時刻 | 自炊か外食か | メニュー | 金額 | 備考 |
|---|---|---|---|---|---|
| 起床 | 必要 | — | — | — | 任意 |
| 朝・昼・晩・間食 | 必要 | 自炊 / 外食 / なし | 複数可 | 外食のときのみ | 任意(店名など) |
| 入眠 | 必要 | — | — | — | 任意 |

**枠に入らないもの:買い物**

買い物は1日の流れの中に位置を持たない。**時刻は記録しない。**

| | 金額 | 中身 |
|---|---|---|
| 食材の買い物 | 必要(合計のみ) | 備考欄に文章で書く(13.6) |

**この考え方に至った経緯**

当初は「記録を時間順に並べたもの」として1日を捉えていた。そのため買い物にも時刻を付け、全てを時間順に並べる形を考えていた。

しかし1日の枠は最初から順番が決まっており、並べ替える必要がない。枠の並びが1日の形そのものである。**この捉え方の違いが、画面の形を大きく変えた**(7.5、7.8)。

**支払い方法を記録しない理由**

当初は外食と買い物で支払い方法(現金・クレジット・PayPay など)を記録することにしていたが、**取りやめた。**

4.4 にある「レシートが出ない支払いがあって記録が漏れる」という元の課題は、**記録が漏れることの問題**であって、支払い方法そのものを記録したいという話ではなかった。手で記録する仕組みを作った時点で解決している。

→ 必要になれば後から足せる。

**記録の種類「その他」について**

当初は記録の種類として「外食 / 自炊 / 買い物 / その他」を置いていた。枠という考え方に整理し直した結果、**「その他」の行き場がなくなった。**

起床・入眠が正式な枠になったことで、「その他」が指していたものの多くは吸収されている。**扱いは要確認**(「これから決めること」に記載)。

### 6.2 全部に共通する決まり

- 日付は自由に指定できる。**何年前でも遡って入力できる**(そのための専用の画面は作らない)
- **日付の行はアプリ側が用意する。使う人が記録を置く場所を作る作業をゼロにする**(理由は 10.2)
- 全ての記録に備考欄(自由に書ける)を付ける
- 記録を直せる、消せる
- 金額と食事内容はどちらも任意。片方だけでも保存できる
- **記録していない日と、0円・0件の日を区別する。** 食べなかった時間帯には「**なし**」という選択肢を選んで記録する(これで「記録し忘れ」と「食べなかった」が区別できる。7.4 の数え方の前提になる)
- **時刻は分単位で記録する。** 起床・朝・昼・晩・間食・入眠のすべて。この時刻のばらつきが、生活リズムを測る材料になる(7.7)
- **1回の食事に複数のメニューを登録できる**

### 6.3 「その他」という言葉が2か所で使われている問題 — 決定済み

同じ「その他」という言葉が、違う意味で2か所に出てくる。

| どこ | 選択肢 | 「その他」が指すもの |
|---|---|---|
| 記録の種類(6.1) | 外食 / 自炊 / 買い物 / **その他** | 外食でも自炊でも買い物でもない記録 |
| 食事の時間帯(7.2) | 朝 / 昼 / 晩 / **その他** | 朝昼晩に当てはまらない時間に食べたもの |

この2つは別の軸を表している。時間帯は「いつ食べたか」、種類は「何をしたか」。間食をコンビニで買って食べれば、時間帯は「その他」で種類は「外食」になる。

**決定:時間帯の方の名前を「間食」に変える。**

理由は3つ。

1. 朝昼晩以外に食べるものは、ほとんどが間食か夜食であり、夜食も間食として扱える
2. 「その他」より具体的で、何を入れるか迷わない
3. 画面に出すときも短く収まる

これにより「その他」という言葉は記録の種類だけに残り、混同がなくなる。

---

## 7. 画面に出すもの

### 7.1 最小限の機能

1. 支出の記録
2. 食事の記録
3. 記録を直す・消す
4. 一覧と振り返り(中身は 7.2)
5. 通知(記録の状況を見せる)

### 7.2 振り返りに出すもの

| 面 | 出すもの |
|---|---|
| 出費 | **期間ごとの食費の合計を、棒グラフで並べて見せる**(詳しくは 7.6) |
| 食事 | **日ごとに枠が並び、時刻・自炊か外食か・メニューが読める**(形は 7.8) |
| 食事の安定 | **自炊と外食の比率 / 食事時刻のばらつき**(詳しくは 7.7) |
| 続き具合 | **記録日数を3つの数字で出す** — 累計 / 今月 / 連続(最高記録つき)。完了した日の判定は 7.4、3つの数字の詳細は 10.3 |

**どこまで見せるか**

- **直近1週間**: 何も押さなくても中身が見える
- **それ以前**: 範囲を切り替えれば、全ての記録を見られる(7.8)

### 7.3 振り返りの単位

- 振り返りは**日・週・月で切り替えられる**(日は 7.6 のグラフで追加)
- 基本で表示するのは「**今週**」「**今月**」
- 「**先週**」「**先月**」も選べる
- **全ての記録を見る画面は別に用意する**
- **その日の記録を見る画面とは別の画面にする**

→ ここから、振り返り系の画面は少なくとも3種類に分かれる見込み。画面のつながりを決める作業(第3部 12)で確定させる。

1. 週や月の振り返りを見る画面(今週・今月・先週・先月を切り替え)
2. その日の記録を見る画面(提案は 7.5)
3. 全ての記録を見る画面

### 7.4 記録日数の数え方(決定済み)

**アプリ側で自動的に判定する。「今日は終わり」のようなボタンは作らない。**

```
朝・昼・晩・間食の4つの時間帯すべてに記録がある日 = その日は完了 → 記録日数に数える
  ※「なし」も記録の一種として数える
1つでも記録していない時間帯がある日 = 未完了
```

**なぜこれで判定できるか:** 食べなかった時間帯には「**なし**」を選んで記録する(6.2)。欠食が「記録がない状態」ではなく「なしという記録がある状態」になるため、記録し忘れと区別できる。判定に必要な情報が存在するので、自動で判定できる。

**買い物について:** 時間帯に属さない記録なので、完了の判定には関係しない(買い物をしなかった日も、4つの時間帯が埋まっていれば完了)。

→ 「この日は完了した」という印をデータに持つ必要はない。4つの時間帯が埋まっているかを記録から計算すればよい。

### 7.5 その日の画面(決定済み)

1日の枠(6.1)をそのまま並べる。**記録を見る場所であり、入れる場所でもある。**

```
10月13日(月)

 起床    7:05
 ──────────────────────────────────
  朝     8:12   自炊   目玉焼き、味噌汁
  昼    12:40   外食   ラーメン、餃子       ¥900
  晩    19:30   自炊   カレー
  間食    ―      ―      ―
 ──────────────────────────────────
 入眠   23:40

 買い物   スーパー                        ¥2,340
 この日の出費                             ¥3,240
```

- 起床と入眠が食事の枠を挟む。これが1日の形
- **買い物は枠の外。時刻は出さない**
- その日の出費の合計も枠の外

**入力の仕方:Excel のように、押したところに直接打つ**

別の画面に移らない。下からせり上がる入力欄も出さない。**押したセルにその場で打つ。**

- 自炊か外食かの欄を押す → 自炊 / 外食 / なし の選択肢が出る
- 時刻の欄を押す → 時刻の選び方が出る
- メニューの欄を押す → そのまま文字が打てる

**記録していない枠と「なし」は別の見た目にする**

記録していない枠は空欄、食べなかった枠は「なし」。6.2 で区別すると決めているので、画面でも分ける。

**備考をどこに置くか**

横幅に入らないため、**行の右端に小さな印を置き、押すと備考だけが開く**形にする。備考を書く日は少ないので、普段は邪魔にならない。

**記録1件だけの画面は作らない(決定済み)**

当初は、行を押すと記録1件の画面が開く形を考えていた。取りやめた。画面を移る必要がなく、その場で打てれば足りるため。

→ これにより **12.4 の矛盾が解消する。** 入力専用の画面が要らなくなり、「入力画面1つ + 表示画面2つ」という当初の構成は、この画面に統合される。

### 7.6 推移を見るグラフの画面

**この画面が「変化を見る」役目をすべて引き受ける。**

#### 今回作る範囲(決定済み)

**生活習慣における出費の動向を見える化すること。** これに絞る。

起床・入眠・食事の時刻をグラフにするのは、今回は作らない。ただし**後から足せる形を想定して作る。**

#### この画面が答える問い(重要)

**合計の出費が実際に減っているか。変動はどうなっているか。それを確かめて次につなげる。**

→ **外食を減らすことが目的ではない。** 重要なのは合計の出費である。

7.7 で「自炊と外食の比率」を見ると決めているが、あれは**健康の面**(安定した食事がとれているか)の材料であって、お金の面の材料ではない。4.2 の2つの目的のうち、どちらに属するかを混同しないこと。

| 目的 | 見るもの | どこで見るか |
|---|---|---|
| 無駄なく抑えられているか(お金) | **合計の出費と、その変動** | この画面(7.6) |
| 安定した食事がとれているか(健康) | 自炊と外食の比率、食事時刻のばらつき | 7.7 |

#### 画面の中身(決定済み)

```
 出費の動向

 [ 日 ]  [ 週 ]  [ 月 ]          ← 期間の単位

 ◀  2026年  ▶                    ← 年の切り替え

        ┌──────────────┐
        │  9月    ¥16,756   ▶│   ← 選んだ期間
        └──────────────┘

  (万)
   2 ┤                █
   1 ┤   █ █ █   █ █  █  █
   0 └──────────────────
     1月 2月 3月 ... 9月 10月

 ──────────────────────
  この期間の記録を見る   →        ← 7.8 へ移動
```

| 決めたこと | 内容 | 理由 |
|---|---|---|
| 見出し | **「出費の動向」** | 下記の育ち方Bを採るため |
| 平均 | **出さない** | 数字で出されても判断の材料にならない。並べて見れば分かる |
| 日を選んだときに並べる本数 | **その月の日数分** | 月の切り替えと動きが揃う。日は月を切り替え、週と月は年を切り替える |
| 選んだ棒 | 色を濃くし、上に金額を大きく出す | 挙がった銀行アプリの画面と同じ |

#### 出費の種類が増えたときの育ち方(決定済み:B)

将来、交通費やサブスクを記録するようになったときの2つの育ち方。

| 育ち方 | 形 | 採否 |
|---|---|---|
| A | 「食費のグラフ」「交通費のグラフ」と項目が横に並ぶ | 不採用。種類が増えるたび項目が増える。合計を見る場所がない |
| **B** | **「出費」という1つの場所があり、中で種類を切り替える** | **採用** |

```
[ 出費 ]  [ 起床 ]  [ 入眠 ]       ← 何を見るか(上の段)
   └ [ 全部 ] [ 食費 ] [ 交通費 ]   ← どの出費か(下の段)
```

Bを採る理由は2つ。

1. 項目が横に増え続けない。出費の種類が10個になっても、上の段は「出費」のまま
2. **「全部でいくら使ったか」が見られる。** Aだと食費と交通費を足す場所がない。合計の出費こそが重要なので、これが決め手になった

今は出費の種類が食事関係しかないので、**どちらの段の切り替えも画面に出ない。** 種類が増えたときに現れる。

#### 将来の姿

最終的に「タスクや生活習慣全般を一括管理する」という目標からすると、**この画面が一番伸びる。** 数値になるものはすべてここに乗る。

| 見るもの | 数値の性質 | 合う形 | 今回作るか |
|---|---|---|---|
| **出費(食費)** | **量。足し算できる** | **棒グラフ** | **作る** |
| 起床・入眠・食事の時刻 | 時点。1日の中の位置 | 横軸に24時間を取った形 | 作らない |
| 睡眠時間 | 量(長さ) | 棒グラフ | 作らない |
| タスクの消化 | 量または割合 | 棒グラフ | 作らない |

**切り替えると形も変わる問題**

時刻だけ、数値の性質が違う。量ではなく時点なので、棒の高さで表しても読めない。

そのため「何を見るか」を切り替えると、**グラフの形そのものが変わる**ことになる。これがこの画面の一番難しいところ。今回は出費だけに絞るので、この問題は先送りする。

→ 足すときに改めて形を考える。検討した案は 7.6.1。

**参考にする形**

本人が例として挙げた銀行アプリの画面。次の要素がある。

- 期間ごとの棒が横に並ぶ
- 1本を選ぶと、その期間の金額が上部に大きく出る
- 選んだ棒だけ色が濃くなる
- グラフの下に、全期間の平均額が出る
- 「この月の明細を見る」から、その期間の記録の一覧へ移動できる
- 年を切り替えられる

**なぜ「いつもとの差」ではなくグラフなのか**

当初「過去数ヶ月の平均より +4,200円」のような差の数字を出す案も検討したが、**差を数字で出されても判断の材料にならない**。並べて見たときに初めて「この月は多い」と分かる。

→ 4.2 の「極端に多い月・少ない月を見返して、備考欄を読み、次に活かす」という使い方は、このグラフがないと成立しない。合計だけでは極端さに気づけず、見返すきっかけが生まれない。

**設計への影響(2つ)**

1. **画面を3つ作る必要はない。1つの画面で単位を切り替えればよい。**
   日・週・月は集計する単位が違うだけで、出すもの(期間ごとの食費合計)は同じ。画面を分ける理由がない。

2. **この画面が「一覧」、その先が「詳細」になる。**
   棒を選んでその期間の明細へ移動する流れは、オブジェクト指向UI(12.2)の「一覧から選んで詳細を見る」そのもの。画面のつながりの図にそのまま組み込める。

**作る順番**

時間がかかりすぎるのを防ぐため、段階的に作る(11.3 の方針に沿う)。

1. まず**金額だけの表**を作る(期間と合計金額が並ぶだけ)
2. その後グラフに置き換える

#### 7.6.1 将来、項目を足すときの形(検討した3案)

今回は出費だけなので決めない。足すときに選ぶ。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| 1 | 切り替えで形も変わる。出費なら棒グラフ、時刻ならタイムスケジュール表 | 画面が1つで済む | 切り替えると別物が出るので戸惑う |
| 2 | お金のグラフと生活リズムの図を別の画面にする | それぞれ最適な形にできる。4.2 の目的が2つなので分かれ方も自然 | 画面が増える。12.3 の「画面数を抑える」に反する |
| 3 | 1つの振り返り画面に縦に並べ、スクロールで全部見せる | 切り替えの戸惑いがない。4.2 の「週単位で振り返る」に直接合う | 項目が増えると縦に長くなる |

**時刻を見せるときの形(将来)**

時刻は、棒の高さで表すより**横軸に時間を取った形**が向いている。参考として挙がった「タイムスケジュール表」の形。

```
       0    3    6    9   12   15   18   21   24
 10/13 ─────────◇──□──────△────────○──────●───
 10/12 ─●───────────◇─□─────△─────────○──────
 10/11 ─────────◇□───────△──────○────●───────

   ◇起床  □朝  △昼  ○晩  ●入眠
```

1行が1日。横軸が24時間。印が左右に動くことで、リズムのずれが見える。

**この形に変えることを想定して作る。** ただし最初から作る必要はない(11.3 の段階的に作る方針)。

**まだ決めていないこと**

- 日単位のグラフで何日分を並べるか(1ヶ月分か、もっと短いか)

### 7.7 食事が安定しているかの見方

4.2 の「安定した食事がとれているか」を、**栄養素を見積もらずに判断する。**

栄養素の見積もりは入力の手間が大きく、続かない。代わりに、**既に記録すると決めている情報だけから計算できる数字**を使う。

**採用する2つ**

| 数字 | 何から計算するか | 追加の入力 |
|---|---|---|
| **自炊と外食の比率** | 記録の種類(6.1)を数える | なし |
| **食事時刻のばらつき** | 分単位で記録している時刻(6.2) | なし |

**食事時刻のばらつきを使う理由(3つ)**

1. 4.2 の目的に「リズムを整える」と書いてある。時刻のばらつきは、リズムそのものを測る数字になる
2. 6.2 で「食事の時刻は分単位で記録する」と決めていたが、それが何に使われるかは曖昧なままだった。ここで役割がつく
3. **睡眠の記録を足さなくても、今の仕組みだけでリズムが測れる**

**出し方のイメージ**

```
今週の食事
  自炊 14回 / 外食 5回
  朝食の時刻  7:40 〜 10:20（ばらつき 2時間40分）
  夕食の時刻  18:50 〜 19:30（ばらつき 40分）
```

朝食の時刻が毎日2時間以上ずれているなら、それだけで「リズムが崩れている」と分かる。何を食べたかを分析する必要がない。

**採用しなかったもの(追加入力ゼロで計算できるが、今は使わない)**

欠食の回数、食事の間隔、外食が続いた日数、よく食べるメニュー。
→ 必要になったら足せる。記録は既にあるため。

**将来足すもの**

買ったもの(備考欄の文章)から、栄養の偏りを推測する。8.2 に記載。

### 7.8 全ての記録を見る画面(決定済み)

**その日の画面(7.5)を縦に連ねた形にする。**

```
 10/13(月)                          ¥3,240
   起床  7:05                  入眠 23:40
   朝   8:12   自炊   目玉焼き、味噌汁
   昼  12:40   外食   ラーメン、餃子
   晩  19:30   自炊   カレー
   間食  ―

 10/12(日)                              ―
   起床  9:30                  入眠  1:20
   朝  10:15   自炊   トースト
   ...
```

範囲を切り替えられる(直近1週間 / 1ヶ月 / 全期間)。

**それとは別に、外から期間を指定して開ける必要がある。** グラフ(7.6)で9月を選んで移動したとき、9月を表示した状態で開かなければならない(12.5)。

**なぜ表の形をやめたのか**

当初は、日を縦・枠を横に置いた表を考えていた。

```
        起床     朝      昼      晩     入眠
 10/13   7:05    8:12   12:40   19:30   23:40
 10/12   9:30   10:15   13:00   20:10    1:20
```

この形を却下した理由は2つ。

1. **時刻の数字だけでは見る気が起きない。** 自炊か外食か、記録したかどうかが分からない
2. **変化を見る役目を表に負わせたのが間違いだった。** 変化はグラフ(7.6)で見る。表は中身を読むためのものなので、無理に表の形にする必要がない

**この形の利点**

**日の一覧と全ての記録を見る画面が、1つで済む。** 7.2 で「日ごとに4つの枠で自炊か外食かが分かる」と決めていた画面と、全ての記録を見る画面が、範囲の違いだけになる。

12.3 のオブジェクト指向UIでは「要らない画面は省いて数を抑える」とされている。これに沿う。

**役目の分担(確定)**

| やりたいこと | どの画面 |
|---|---|
| **変化に気づく** | グラフ(7.6) |
| **中身を読む** | 全ての記録を見る画面(7.8) |
| **入れる・直す** | その日の画面(7.5) |

#### 検討して採用しなかった形:カレンダー

Google カレンダーのように月の格子を出し、記録の有無を記号で見せ、日付を押すとその日の画面が開く形を検討した。

```
カレンダー(月)
  各日に ● 完了 / ○ 一部記録 / 空白 未記録 を出す
   └─ 日付を押す → その日の画面(7.5)
```

**採用しなかった理由**

カレンダーが速いのは「**特定の日を探す**」ときである。しかし実際の使い方は「**最近の食生活を振り返る**」ことが多い。4.2 の目的も「週という単位で振り返り、次の週に活かす」であり、特定の日を探す場面ではない。

記録が溜まって流れていく形(7.8)の方が、この使い方に合っている。

**残しておく可能性**

- 日の一覧をカレンダーにする案そのもの。使ってみて「特定の日を探す」ことが多いと分かれば、後から置き換えられる
- **記録の有無を記号で見せる考え方は使える。** 10.3 の記録日数を出す場所に、今月のカレンダーで記録した日に印をつける形なら、中身を読む必要がないので 10.4 の教訓にも反しない

## 10. うまくいったかの測り方

### 10.1 前の状態

**既存の Google スプレッドシートによる記録は、1ヶ月続いて、やめた。**

### 10.2 やめた理由 — 要件に反映済み

スプレッドシートでは、記録するたびに自分で行を足し、日付を書き、書式を整える必要があった。**記録そのものではなく「記録を置く場所を自分で用意する作業」が面倒だった。**

また「シートを作ったとき、ここまで続くと思っていなかった」ため、長く続けることを前提にした作りになっていなかった。

→ 6.2 の「日付の行はアプリ側が用意する」および 9.1「拡張に耐える設計」に反映済み。

### 10.3 目標

前の状態が「1ヶ月続いてやめた」なので、それと比べられる数字にする必要がある。

**使う数字は3つ(決定済み)**

| 数字 | 何が分かるか |
|---|---|
| **累計の記録日数** | 全体でどれだけ記録してきたか。減らない |
| **月あたりの記録日数** | その月の密度。「一応続いているが中身がない」状態を見つけられる |
| **連続日数(最高記録つき)** | 今の勢いと、これまでの最高 |

**画面での出し方**

```
記録日数   累計   87日
          今月   24日 / 31日
          連続   12日（最高 24日）
```

**なぜ連続日数に最高記録を付けるのか**

15 の #6 で「連続日数は主な指標にしない」と決めた。理由は、1日途切れると積み上げがゼロに戻り、再開する気がなくなるため。

連続日数を出すこと自体は #6 と矛盾しない(#6 は「主な指標」についての判断だった)。ただし素直に出すと、1日忘れた翌日に「連続 0日」と表示され、#6 で避けたかった問題がそのまま起きる。

**最高記録を併記すれば、連続が0に戻っても最高記録は消えない。** 「24日続けられた」という事実が画面に残るので、積み上げが全部消えた感覚にならない。

**計算方法**

4つとも記録から計算できる。データに別の印を持つ必要はない(7.4 と同じ結論)。

| 数字 | 計算方法 |
|---|---|
| 累計の記録日数 | 完了した日(7.4)の総数 |
| 月あたりの記録日数 | その月に完了した日数 ÷ その月の日数 |
| 連続日数 | 今日から遡って、連続して完了している日数 |
| 最高の連続日数 | 過去の全記録から、連続して完了した最長の日数 |

### 10.4 前のアプリの見せ方から得た教訓

前のアプリ(my-task-app)では、記録の状況をマス目で見せていた。マス目を押すと日付とその日に達成したかが出る形。**この形は分かりにくかった。**

→ **記録日数は、数字そのものをはっきり出す。** マス目で見せるだけにしない。

# 第3部 どう作るのか

## 11. 進め方の決まりごと

### 11.1 決めたことを記録に残す(ADR)

ADR は Architecture Decision Record の略で、設計上の選択を記録したもの。何かを決めたとき、その判断理由を短いテキストにまとめる。

- **書く内容:** 題名、背景、決めたこと、今の状態、結果、検討した候補、判断の基準、候補同士の比較
- **置く場所:** ソースコードと一緒にリポジトリの中で管理する(コードと記録が同期する)
- **書く対象:** 候補が複数あり、後から見て判断理由が推測しにくいもの

**採用した理由:** README の4項目め「選ばなかった候補も書く」(3.2)と完全に一致する。アプリ自体が仮説を検証する手段でもあるため、後から「この判断が効いた・外した」を振り返る必要がある。

→ ここまでに決めたことは第4部にまとめてある。

### 11.2 参考にした他のやり方

| やり方 | 内容 | 本件での扱い |
|---|---|---|
| ユーザーストーリー | 「<だれ>として、<何か>をしたい。それは<理由>だからだ」の形で要求を書く。専門用語を使わず、画面や処理の方法は書かない | 考え方を参照 |
| ユースケース記述 | 操作の手順や例外の扱いまで含めて「どう動くか」を書く。ユーザーストーリーより細かい | 第2部 5 で実施済み |
| MVP開発 | 需要があるか分からない製品を最小限だけ作り、反応を見て確かめる | **該当しない**。使う人は自分で、需要は分かっている。実態は「要件を絞って小さく作り育てる」やり方 |

### 11.3 作る順番の方針

**最小限の機能を作ってから、後で機能を足したり直したりする方式を採用する。**

検討した2つ。

| 方式 | 内容 | 採否 |
|---|---|---|
| 最初に細かく決めて作り切る | 融通は利かないが手戻りが少ない。仕様が確定している仕事向き | 不採用 |
| **最小限を作ってから足す・直す** | 融通が利く。使いながら要件が固まる | **採用** |

採用した理由: 9.1 の「今あるデータの構造を壊さずに新しい記録の種類を足せること」と一致するため。

#### 前回の失敗との違い(重要)

前回(my-task-app)の失敗の原因は「要件が決まっていなかった」ことだった。この方式はそれと似て見えるが別物。

- 前回: 要件を決めないまま作った
- 今回: **作る範囲を最小限に絞り、その範囲の要件は細かく決める。範囲の外は意図的に保留する**

**保留が「忘れていた」ではなく「意図的に外した」になっているかが分かれ目。** 8.1 の「今回は作らないもの」の一覧がその役割を持つ。範囲の外のものを足すときは、その都度 第2部 と同じ細かさで要件を決めてから着手すること。

### 11.4 作る資料

機能一覧 → **画面のつながりの図** → **画面の中身の配置** → **試作** の4つを作る。

| 資料 | 何を決めるものか | 状態 |
|---|---|---|
| 機能一覧 | 作る機能の範囲 | **終わった**(7.1) |
| 画面のつながりの図 | 画面同士のつながりと分かれ道 | **作業中** |
| 画面の中身の配置 | 情報をどこに置き、何を目立たせるか | これから |
| 試作 | 操作したときの動き | これから |

データの設計図(ER図)は、画面のつながりの図と並行して進められる。ただし機能一覧が固まる前に始めると作り直しになる。

配色や書体を決める資料と、機器や通信の配置を決める資料は、今回は作らない。

## 12. 画面の組み立て方

### 12.1 2つの考え方

| 考え方 | 操作の順序 | 例 |
|---|---|---|
| タスク指向UI | 先に「やること」、後から「対象」 | メールソフトで「新規作成」を押してから宛先を入力する |
| **オブジェクト指向UI** | **先に「対象」、後から「やること」** | メッセージアプリで相手を選んでから送信する |

※ ここでいう「オブジェクト」は、画面の上で使う人が扱う対象物のこと。プログラミングのオブジェクト指向とは別の話。

やることの種類が増えて複雑になるほど、タスク指向UIは目的にたどり着きにくくなるとされている。

### 12.2 採用した考え方と理由

**オブジェクト指向UIを採用する。**

理由は3つ。

1. 単純なアプリにする予定がない。やることの種類が増えるほど、タスク指向UIは目的にたどり着きにくくなる
2. 融通の利く設計にして後から機能を足したり直したりできる構造が求められる。対象を起点にすると画面の数が減り、プログラムも単純になる
3. 8.2 の「あとで足すもの」(起床・就寝・掃除・運動)と相性がよい。タスク指向だと「起床を記録する」「掃除を記録する」とメニューが増え続けるが、オブジェクト指向UIなら「日」という対象の下に枠が増えるだけで、画面の構造は変わらない

### 12.3 作り方の手順

1. **画面で扱う対象を洗い出す** — やりたいことに出てくる名詞を書き出し、重要なものに絞る
2. **画面を2種類に分けて置く** — 一覧を見せる画面と、1件の詳細を見せる画面。この2つの行き来の仕方を図にする。要らない画面は省いて数を抑える
3. **画面の中身を配置する** — 画面の大きさに合わせて置く。置いた後に1〜3を行き来して直す

**手順1の結果(終わっている):** 13.3 の表がその結果にあたる。扱う対象は次の3つ。

| 対象 | 根拠 |
|---|---|
| 日 | 13.3 の全ての記録が「日付」を共通して持つ |
| 記録 | 13.3 の各行(外食・自炊・買い物、あとで起床・就寝・掃除・運動) |
| メニュー | 13.2、13.3(1回の食事に複数ぶら下がる) |

### 12.4 画面の構成 — 解消済み

**以前に決めたこと(オブジェクト指向UIを採用する前)**

- 入力画面: 1つ(種類を選び、必要な項目だけ入力する)
- 表示画面: 出費と食事で分ける(金額のあるものは出費の画面、食事内容のあるものは食事の画面)

**何が矛盾していたか**

オブジェクト指向UIでは、一覧から対象を選び、その詳細の画面で記録を見ることも入れることも行う。**入力だけの画面が独立して存在しない**ため、「入力画面1つ + 表示画面2つ」という構成は成り立たなかった。

この矛盾は、上の決定をした時点でオブジェクト指向UIという選択肢が出ていなかったために生じた。

**どう解消したか**

その日の画面(7.5)が、見る場所と入れる場所を兼ねることになった。押したところに直接打つ形にしたため、入力専用の画面が要らない。

「出費と食事を分けて見たい」という要求は、画面を分けるのではなく**役目を分ける**形で満たした(7.8)。

| やりたいこと | どの画面 |
|---|---|
| 変化に気づく | グラフ(7.6)。出費・起床・入眠・食事の時刻を切り替えて見る |
| 中身を読む | 全ての記録を見る画面(7.8) |
| 入れる・直す | その日の画面(7.5) |

**確定した画面の一覧**

| 対象 | 一覧 | 1件 |
|---|---|---|
| 日 | 全ての記録を見る画面(7.8)。範囲を切り替えられる | その日の画面(7.5) |
| 期間(日/週/月) | グラフ(7.6) | その期間の記録 → 7.8 へ |
| 記録 | 作らない。日の中に収まる | 作らない。その場で打つ(7.5) |
| メニュー | **作らない。** 7.7 で「メニューを横断して集計する画面は作らない」と決めたため | 作らない |

**これで画面のつながりを決める作業は終わり。** 次は画面の中身の配置。

### 12.5 画面の行き来(決定済み)

#### 2つの流れ

```
【毎日】
 アプリを開く → その日の画面(7.5) → 記録を入れる

【ときどき】
 グラフ(7.6)
   │  変化が激しい日・月を見つける
   ↓  その棒を選んで「この期間の記録を見る」
 全ての記録を見る画面(7.8)
   │  選んだ期間を表示した状態で開く。備考を読む
   ↓  日を選ぶ
 その日の画面(7.5)
```

#### 下部のタブで行き来する

グラフは毎日見るものではない。記録とは別の用事で開く。

```
 ┌──────────────────────┐
 │                            │
 │        画面の中身           │
 │                            │
 ├──────────────────────┤
 │   今日    記録     グラフ    │
 └──────────────────────┘
```

| タブ | 開く画面 | いつ使うか |
|---|---|---|
| **今日** | その日の画面(7.5) | 毎日。記録を入れる |
| 記録 | 全ての記録を見る画面(7.8) | 振り返るとき |
| グラフ | グラフ(7.6) | 変化を見るとき |

**最初に出るのは「今日」。** 4.3 の最優先条件が「利用頻度が高いこと」であり、毎日やることは記録だから。開いた瞬間に記録できる状態にあるのが、一番摩擦が少ない。

#### ここから出てくる作り方の条件

**全ての記録を見る画面(7.8)は、外から期間を指定して開ける必要がある。**

グラフで9月を選んで移動したとき、7.8 が最新の記録から始まっていては意味がない。9月を表示した状態で開かなければならない。

7.8 は範囲を切り替えられる形(直近1週間 / 1ヶ月 / 全期間)だが、それとは別に、**特定の期間を指定して開く入口**が要る。

## 13. データの持ち方

### 13.1 前提にしている知識

- 表は行と列からできている、という理解がある
- 複数の表を関連付ける話は聞いたことがある
- 関連付けの具体的な方法(各行に重複しない番号を振り、相手の表からその番号を参照する)は 13.2 で確認済み

### 13.2 表を分けて結びつける方法

表の全体を指すのでは足りず、**その表のどの行を指すか**を特定する必要がある。各行に重複しない番号を振り、相手の表にその番号を書く。

**食事の表**

| 番号 | 日付 | 時間帯 | 時刻 | 種類 |
|---|---|---|---|---|
| 1 | 10/3 | 晩 | 19:30 | 外食 |
| 2 | 10/3 | 朝 | 8:00 | 自炊 |

**メニューの表**

| 番号 | どの食事か | メニュー名 |
|---|---|---|
| 1 | 1 | ラーメン |
| 2 | 1 | 餃子 |
| 3 | 2 | 目玉焼き |

これで「1回の食事に複数のメニュー」が、メニューの表に行を足すだけで表せる。

1つの表に `メニュー1`〜`メニュー3` と列を並べる形だと、4品食べた日に列を足す必要があり、ほとんどの行が空欄になり、「餃子を何回食べたか」の集計も難しくなる。

### 13.3 データは2種類に分かれる

**これが設計の軸になる。**

| | 1つの記録につき | 例 |
|---|---|---|
| **単一のもの** | 必ず1つ | 時刻、自炊か外食か、金額、備考 |
| **複数ぶら下がるもの** | 0個から何個でも | メニュー、掃除の場所、タスク |

単一のものは表の列にできる。複数のものは列にできない。列にしようとすると「メニュー1、メニュー2、メニュー3」という形になり、13.4 の2案目の失敗に戻る。

#### 記録の種類ごとの中身

| 記録 | 日付 | 時刻 | 単一のもの | 複数ぶら下がるもの |
|---|---|---|---|---|
| 起床 | あり | あり | — | — |
| 入眠 | あり | あり | — | — |
| 食事 | あり | あり | 枠(朝/昼/晩/間食)、自炊か外食か、金額(外食のみ) | メニュー |
| 買い物 | あり | **なし** | 金額 | — |
| (将来)掃除 | あり | あり | — | 場所 |
| (将来)運動 | あり | あり | 時間 | 種目 |
| (将来)タスク | あり | ? | 未定 | 未定 |

**共通するのは「日付」と「何の記録か」。時刻もほぼ共通(買い物だけない)。それ以外は種類ごとにばらばら。**

### 13.4 検討した3つの案

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| 1案目 | 種類ごとに表を完全に分ける | 各表が単純。新しい種類を足すとき既存の表に触らない。壊す危険が最も小さい | 1日の全記録をまとめて見るとき、全ての表から集める必要がある |
| 2案目 | 1つの表に全ての列を置き、使わない列は空にする | 作るのが簡単 | 空欄だらけになる。新しい種類のたび列が増え続ける。**3.1 の指摘にあった失敗例そのもの** |
| **3案目** | **共通の表1つ + 種類ごとの表** | 1日の全記録を時間順に見るのが簡単。新しい種類を足すときは種類ごとの表を足すだけで、共通の表は変わらない | 表の数が増える。1件取り出すのに複数の表を見る必要がある |

**2案目は除外。** 3.1 で批判されていた形であり、懸念していた「壊れる」形そのもの。

### 13.5 決めた形(確定)

**3案目(共通の表 + 種類ごとの表)。**

```
記録の表
  id / 日付 / 時刻 / 種類 / 金額 / 備考

食事の表
  記録id / 枠 / 自炊か外食か

メニューの表
  id / 記録id / メニュー名
```

#### 各列を置いた理由

**記録の表**

| 列 | 理由 |
|---|---|
| id | 他の表から指すため(13.2) |
| 日付 | すべての記録が持つ |
| 時刻 | 起床・入眠・食事が持つ。買い物は空欄(6.1 で時刻を記録しないと決めた) |
| 種類 | 起床 / 入眠 / 食事 / 買い物 |
| 金額 | 外食と買い物が持つ。**7.6 の出費合計を、この列を足すだけで出すため** |
| 備考 | すべてに付ける(6.2)。買い物の中身もここ(13.6) |

**食事の表**

| 列 | 理由 |
|---|---|
| 記録id | どの記録のものか |
| 枠 | 朝 / 昼 / 晩 / 間食。7.4 の完了判定に使う |
| 自炊か外食か | 自炊 / 外食 / なし。7.7 の比率に使う |

**メニューの表**

| 列 | 理由 |
|---|---|
| id | 1行を特定して消すため |
| 記録id | どの食事のものか |
| メニュー名 | 名前だけ |

#### 実際にデータを入れた例(10月13日)

**記録の表**

| id | 日付 | 時刻 | 種類 | 金額 | 備考 |
|---|---|---|---|---|---|
| 1 | 10/13 | 7:05 | 起床 | | |
| 2 | 10/13 | 8:12 | 食事 | | |
| 3 | 10/13 | 12:40 | 食事 | 900 | 二郎系 |
| 4 | 10/13 | 19:30 | 食事 | | |
| 5 | 10/13 | | 食事 | | |
| 6 | 10/13 | | 買い物 | 2340 | 鶏むね肉、キャベツ、米5kg |
| 7 | 10/13 | 23:40 | 入眠 | | |

**食事の表**

| 記録id | 枠 | 自炊か外食か |
|---|---|---|
| 2 | 朝 | 自炊 |
| 3 | 昼 | 外食 |
| 4 | 晩 | 自炊 |
| 5 | 間食 | なし |

**メニューの表**

| id | 記録id | メニュー名 |
|---|---|---|
| 1 | 2 | 目玉焼き |
| 2 | 2 | 味噌汁 |
| 3 | 3 | ラーメン |
| 4 | 3 | 餃子 |
| 5 | 4 | カレー |

id=5 は間食の「なし」。食べていないので時刻も金額もない。これは**意味のある空欄**であり、13.4 の2案目で問題にした「空欄だらけ」とは違う。

#### 複数ぶら下がるものを、種類ごとに別の表にする(決定済み)

将来、メニュー・掃除の場所・タスクが同じ形で現れる。2つのやり方を検討した。

| やり方 | 形 | 採否 |
|---|---|---|
| **A** | **種類ごとに別の表**(メニューの表 / 掃除場所の表 / タスクの表) | **採用** |
| B | 1つの表にまとめる(項目の表:記録id / 内容) | 不採用 |

**Aを採る理由:タスクが名前だけで済まない可能性が高い。**

メニューと掃除の場所は名前だけ(「ラーメン」「風呂」)。しかしタスクは、終わったかどうか、いつまでにやるか、といった情報が付くかもしれない。目標が「タスクや生活習慣全般を一括管理する」なので、その可能性がある。

Bでまとめた後にタスクだけ列が必要になると、その列はメニューの行にも掃除場所の行にもできる。13.4 の2案目の失敗が、小さい規模で起きる。

**分かれているものをまとめるのは簡単だが、まとめたものを分けるのは、既に入っているデータを動かす必要がある。**

#### 将来足すときに何が起きるか

| 足すもの | やること | 記録の表を触るか |
|---|---|---|
| 掃除 | 種類に「掃除」を足す。掃除場所の表を1つ作る | 触らない |
| 運動 | 種類に「運動」を足す。運動の表を1つ作る | 触らない |
| タスク | 種類に「タスク」を足す。タスクの表を1つ作る。形が未定でも、そのとき決められる | 触らない |
| 交通費など別の出費 | 種類を足す。金額は既にある列を使う | 触らない |
| 複数人での利用 | 利用者の列を1つ足す | **1列だけ足す** |

複数人だけ記録の表に手が入るが、1列足すだけで済む。既にあるデータは全部自分のものとして埋めればよい。

#### 「その他」という種類は置かない(決定済み)

何でも入る箱を作ると、本来は新しい種類として足すべきものがそこに溜まる。後から「これは掃除だった、これは運動だった」と分けようとしても分けられない。

新しい記録が必要になったら種類を足せばよい。上の表のとおり、それができる形になっている。**箱を用意しておく必要がない。**

#### 「日」の表は作らない(決定済み)

日付は記録の表が持っている。その日が完了したかは、食事の表を見て枠が4つ揃っているかを数えれば出る(7.4 で「印をデータに持つ必要はない」と決めた通り)。

将来「その日のひとこと」を書きたくなったら、そのとき作る。

### 13.6 買い物の中身をどう持つか(決定済み)

**1つの文章(文字列)として備考欄に持つ。品物ごとに行を分けない。**

食事のメニューは行を分ける(13.2)のに、買い物の品物は分けない。この違いの理由。

| | 何のために記録するか | 必要な細かさ |
|---|---|---|
| 食事のメニュー | 安定した食事がとれているかを見る(4.2) | 1品ずつ。何を食べたかの積み重ねが判断材料になる |
| 買い物の品物 | 無駄なく抑えられているかを見る(4.2) | 期間ごとの合計で足りる。品物ごとの集計は 8.1 でスコープ外 |

**目的に対して必要な細かさが違う。** これが行を分けるかどうかの判断基準になっている。

**補足:文章で持つことは、行を分けることの劣化版ではない**

備考欄に「鶏むね肉、キャベツ、米5kg」と書いてあれば、本当に品物ごとの集計がしたくなったとき、その文章から拾える。最初から入力しなければデータは存在しない。つまり**判断を先送りできる形**であり、11.3「最小限を作ってから足す」と一致する。

**書き方に決まりは作らない**

決まりを作ると入力の手間が増え、続かなくなる(2.3「怠惰は直さない」)。代わりに、入力欄に例を薄く表示して書き方を思い出させるだけにする(例:「米5kg、鶏むね肉、調味料」)。強制しないので手間は増えない。

### 13.7 この設計に付いている名前

面接で聞かれたとき用。中身は上で説明したとおり。

| 名前 | 中身 |
|---|---|
| 正規化 | 1つのマスに1つの値だけ入れる。同じ値を2か所に書かない |
| 第1正規形 | 1マス1値。メニューを別の表にしたのがこれ |
| 具象クラス継承 | 13.4 の1案目(種類ごとに完全に別の表) |
| 単一テーブル継承 | 13.4 の2案目(1つの表に全部) |
| **クラステーブル継承** | **13.4 の3案目(共通の表+種類ごとの表)。採用したもの** |
| ポリモーフィック関連 | 子の表が「どの表を参照しているか」を列に持つ形。参照先が複数になり、整合性を保証できなくなるためアンチパターンとされる。**この設計では、参照先が常に記録の表1つなので該当しない** |

### 13.7.1 通知の送り先を保存する表(決定済み)

14.7.1 の調査で、**この3つの表には通知の送り先を保存する場所がない**ことが分かった。4つ目の表を足す。

#### なぜ必要なのか

通知は「このアプリに送る」という形では送れない。**「この端末のこのブラウザに送る」**という形でしか送れない。

```
1. アプリを開いて「通知を許可」を押す
       ↓
2. その瞬間、この端末専用の送り先が1つ発行される
       ↓
3. その送り先を保存しておく        ← この表が要る
       ↓
4. 毎晩21時、保存した送り先に向けて通知を送る
```

送り先はこういう長い文字列である。

```
https://web.push.apple.com/QHxGf9kZ...(以下100文字ほど続く)
```

**自分で決められない。** 2番の瞬間に自動で発行されるもので、端末ごとに違う。保存しないと、4番の時点で送り先が分からなくなる。

#### なぜ既存の3つの表に入れられないのか

今の3つの表は、全部「その日何を食べたか」の記録である。送り先はそれとは別のもので、日付とも食事とも関係がない。記録の表に送り先の列を足すと、記録1件ごとに送り先が入ることになり、意味が合わない。

#### この表が使われる場面

| 場面 | この表に対して何をするか | 頻度 |
|---|---|---|
| 通知を許可した | 1行足す | 端末ごとに1回 |
| **毎晩21時** | **全部読む** | **毎日。これが主な用途** |
| 送信に失敗した | その行を消す | たまに |
| 通知を切った | その行を消す | ごくたまに |

**書き込みはほとんど起きない。ほぼ読むだけの表である。**

#### 決めたこと(5件)

**1. 複数の端末に送るか → 登録されている送り先、全部に送る**

1件だけ持つ案(新しい送り先が来たら古いのを消す)は採らない。パソコンで一度開いただけでiPhoneに届かなくなる。**本来届くはずの端末で届かなくなる事故のほうが、同じ通知が2回届く煩わしさより重い。**

14.6 で「通知は補助、開いた瞬間の画面が本体」と決めているため、2回届いても実害はない。

**2. 古い送り先の片付け方 → 送信に失敗したら、その行を消す**

機種変更すると、古い端末の送り先が表に残り続ける。これを片付ける方法。

送信すると「この送り先はもう無効です」という返事が返ってくるので、それを受け取った行を消す。**これが唯一、確実な方法である。** 送り先が有効かどうかは、送ってみないと分からない。

| 選ばなかった案 | 理由 |
|---|---|
| 一定期間たったら消す | 使い続けている端末を誤って消す可能性がある |
| 片付けない | 機種変更のたびに行が増え続ける。2.3 の「サボれない仕組みにする」に反する |

**3. 通知を切ったとき → 行を消す**

「オフ」の印をつけて行を残す案は採らない。列が1つ増えるのに対し、得られるのは「再びオンにするとき送り先を取り直さずに済む」だけで、取り直しは一瞬で終わる。11.3 の「最小限を作ってから足す」に沿う。

**4. 同じ送り先が2回登録されたら → 送り先は重複できない決まりにする**

同じ端末で通知を許可し直すと、同じ送り先が返ってくることがある。そのまま2行入れると同じ端末に同じ通知が2回届く。同じものが来たら、登録日時だけ更新する。

**5. 将来のログインに備えて利用者の列を今入れるか → 今は入れない**

13.5 で、記録の表も利用者の列を今は持たない形にしている。**この表だけ先に入れると扱いがちぐはぐになる。** 8.1 で「今回はログインを作らない」と決めているため、両方そろえて後から足す。

#### 決めた形(確定)

```
送り先の表
  id       番号
  送り先   通知の送り先。重複できない
  登録日時 いつ登録したか
```

**3列だけ。**

| 入れなかったもの | 理由 |
|---|---|
| 端末の名前 | 使い道がない。全部に送るので区別が要らない(決めたこと1) |
| オンかオフか | 行を消すので不要(決めたこと3) |
| 最後に送れた日時 | 失敗したら消すので、残っている行は有効(決めたこと2) |
| 利用者 | 後から足す(決めたこと5) |

#### 9.1 の検証結果

**既存の3つの表には一切手を触れていない。表を1つ足すだけで済んだ。**

9.1 の「既存のデータ構造を壊さずに、新しいものを追加できる設計であること」が、最初の実例で満たされた。

**ただし今回は条件が易しい例である。** 送り先は記録と全く関係がないため、ぶつかりようがなかった。本当の試練は、将来「起床・就寝時刻」や「掃除した場所」を足すとき(8.2)。あれは記録の仲間なので、13.5 の共通の表に乗るかどうかが問われる。

### 13.8 まだ決めていないこと

- タスクの形(単一の項目として持つか、複数ぶら下がるものとして持つか)。足すときに決める

## 14. 技術の選び方と、いつ選ぶか

### 14.1 一般的にはどの工程で決めるか

システム開発の工程では、技術や構成の選定は「**方式設計**」という工程で行う。要件定義で決まった内容を、どういう構成や技術で実現するかを決める工程で、ソフトウェアの選定、通信の構成、外部のシステムとのつなぎ方を決める。性能や障害への対策もここで検討する。

要件を決める工程では技術を決めない。画面構成や入出力を決める工程でも決めない。

### 14.2 選び方の手順

1. **前提条件を整理する** — 要件に加えて、締め切りとその余裕、外してもよい仕様、自分が今使える技術、再利用できる資産、似ている既存のプロダクトを確認する
2. **新しい技術が本当に必要か判断する** — 使い慣れた技術で足りるなら、その方が慣れ・再利用・保守の面で有利
3. **選定にかける時間を先に決める** — 選定に時間をかけるほど、実装にかけられる時間が減る
4. **候補を探す** — まず第一候補を決め、「○○ vs」で検索したり比較サイトを見て、対抗する候補を挙げる。見つからなかったものは検討から外してよい
5. **候補を比べる** — 要件を満たすか / 既存の技術との相性 / 運用にかかる費用 / 開発が活発か / 自分のやる気
6. **試作する** — **最も複雑で難しい部分から着手する。** 後半になって「要件を満たせない」と分かるのを防ぐため。また「ここを過ぎたら第二候補に戻れない」という線を先に決めておく
7. **仕上げる**

### 14.3 個人で作るときの注意

- 最初に動くものを出すことを優先する。使い慣れたものを恐れず使う
- 迷ったら楽しい方を選ぶ。個人で作る場合、続けられることが最も重要
- **調べすぎない。** 比較に時間をかけすぎると動けなくなる。ざっくり調べて選び、試しながら学ぶ
- 判断材料になるもの:公式の説明書が詳しいか / やり取りが荒れていないか / 開発が活発か(最終更新が半年〜1年以上前のものは避ける)
- **GitHub のスターの数は参考にしない。** 新しさや話題性を示すもので、続くかどうかとの関係は薄い
- 自分で作らず既存のライブラリを使う。自作は時間を取られやすい

### 14.4 新規開発であることの意味

新規開発は、技術的な負債がゼロの数少ない機会であり、ここでの決定は重い。候補を広げてから絞る。

**選ばなかった理由を説明できるようにしておくこと。それが決定の正当性になる。**

→ これは 11.1 の決定の記録(ADR)と、3.2 の README の4項目めと一致する。

### 14.5 本プロジェクトでいつ決めるか — 提案

**画面のつながりとデータの設計が決まった後、試作に入る前。**

理由は4つ。

1. 工程としては要件を決めた後に来る(14.1)。本件の要件は決まっている
2. 画面とデータが決まっていないと、「要件を満たすか」という最も重要な基準で候補を比べられない
3. 試作は実際のコードで作る以上、何で作るか決まっていないと着手できない
4. 選定した理由を要件から導ける状態になる。これは選考で問われる部分(3.2)

**あわせて決めること:選定にかける時間の上限。**

これを決めないと、調べすぎて動けなくなる(14.3)。一方で、時間を切りすぎると前回の失敗「早く完成させることにこだわった」(2.2)の再来になる。どちらにも倒れない時間を、選定を始める前に決めておく。

## 14.6 前提条件の整理と、作る形の決定(2026-10-14)

14.2 の手順1〜3にあたる作業。結果だけでなく、選ばなかった候補と理由も残す。

### 前提条件(手順1)

要件のうち、技術の候補を絞る条件として効くものを抜き出した。

| 出どころ | 条件 | 何を縛るか |
|---|---|---|
| 9.2 | スマートフォンで使う | 作る形そのもの |
| 9.2 | 年内に完成 | 学習量の上限 |
| 9.2 / 4.1 | 選考で技術的な判断を説明できる水準 | 「動けばいい」選び方ができない |
| 7.1 / 5 | 通知が要る。1日1回の操作なので1回逃すと1日分が抜ける | **実現手段が限られる。最大の制約** |
| 13.5 | 表3つ。行どうしを番号で結びつける形 | データの保管場所の種類 |
| 10.3 / 7.4 | 記録日数(累計・今月・連続)と出費の合計を計算して出す | 計算をどこでやるか |
| 9.1 / 8.2 | 後から記録の種類と表を足せる | 保管場所の変えやすさ |
| 8.2 | ログインと利用者ごとの分離を、後から足せる | **保管場所の選び方に直結する** |
| 6.2 | 何年前でも遡って入力できる | データが消えない前提が要る |

**本人の環境**

- 普段使うスマートフォンは iPhone
- 開発に使うパソコンは Windows
- 前に作った my-task-app は全体をAIが生成したもので、本人の技術力としては残っていない

### 手順2の基準を置き換えた(重要)

14.2 の手順2は「使い慣れた技術で足りるなら、その方が有利」である。しかし使い慣れた技術が存在しないため、この手順はそのまま適用できない。そこで基準を置き換えた。

> **「自分が慣れているか」ではなく、「詰まったときに、AIに書かせずに自力で調べて解決できるだけの情報が世の中にあるか」で選ぶ。**

2.2 の「AIが書いたコードを見直さなかった」を繰り返さないための基準である。

### 選定にかける時間の上限(手順3)

**数日。** 候補を挙げた後、実際に少し触ってから決める。

### 作る形の決定

**ホーム画面に追加して使うWebアプリにする。**

Webアプリとは、ブラウザで開いて使うアプリのこと。本体はインターネット上にあり、端末にダウンロードしない。「ホーム画面に追加」は、そのURLを開くためのアイコンをホーム画面に置く仕組みで、押すとアドレス欄や戻るボタンが消えた状態で開く。前に作った my-task-app もこの形だった(1.1 の `vite-plugin-pwa` がこれにあたる)。

**なぜこの形になるのか — 通知から決まった**

7.1 の通知は「入力を促す」ものではなく「その日の記録の状況を見せる」ものである。つまり**通知を作る側が、その日何が記録されているかを読める必要がある。**

| 形 | 通知の出し方 | データの置き場所 |
|---|---|---|
| ホーム画面に追加するWebアプリ | アプリを開いていない間に端末が自分で通知を出せない。**外のコンピュータから送る** | **インターネット上に置くことが必須**(通知の中身を作るため) |
| ストアから入れるアプリ | 端末の中で時刻を指定して予約できる | 端末の中だけでも成立する |

iPhoneでWebアプリの通知を使うには条件がある。iOS/iPadOS 16.4 以降で、ブラウザの共有ボタンから「ホーム画面に追加」を行い、そこから開いた状態でないと、通知の許可を求めることすらできない。Safariで普通のサイトとして開いているだけでは受け取れない。**自分の端末で一度やれば済む作業**なので、今回の支障にはならない。

### 選ばなかった形と、その理由

**ストアから入れるアプリ(iPhone向け)**

| 項目 | 内容 |
|---|---|
| 作る環境 | Appleの開発道具はMacでしか動かない。インターネット上のMacを借りる仕組みを使えばWindowsからでも作れるが、本題と関係ない仕組みの学習が乗る |
| 費用 | 自分のiPhoneに入れ続けるには有料登録が要る。無料のままだと7日で期限が切れて使えなくなる。年会費は99ドル、2026年時点で日本円にして約14,000〜15,000円 |
| 審査 | App Storeには「最低限の機能」という基準(ガイドライン4.2)がある。アプリはWebサイトを包み直したものを超える機能・中身・画面を持つべきで、特に便利でもなく独自性もなく「アプリらしく」もないなら相応しくない、という内容 |
| 今回との相性 | 7.1 で機能を5つに絞り、11.3 で「最小限を作ってから足す」と決めている。**この進め方は審査基準と正面からぶつかる** |

さらに、Webサイトを包んだだけのアプリに対する却下の文面には、プッシュ通知や位置情報や共有といった機能を入れても相応しいとは言えない、基準に合わせないのであれば代わりにWebアプリを作って自分のサイトで配布すればよい、App Storeはウェブアプリを受け付けないし配布もしない、と書かれている。**今回のWebアプリをそのまま包んでストアに出す道は塞がれている。**

決め手は費用ではなく、**9.2 の「年内完成」を、自分では縮められない審査の待ち時間に預けることになる**点である。何回で通るか読めない。

**ストアから入れるアプリ(Android向け / Google Play)**

審査自体はApp Storeより緩い。しかし**本人のスマートフォンがiPhoneなので、自分で毎日使えない。** 4.3 の「利用頻度が高いこと」と 10.3 の記録日数は、自分が毎日使って初めて成立する。この時点で前提が崩れる。

加えて、個人の開発者アカウントは、正式公開の前に非公開のテストを行う必要があり、申請の時点で一定数(12〜20人)のテスターが参加し、直前の14日間続けて参加している状態でなければならない。費用は一度きりの登録料で、毎年かかるものではない。ただし上の2点は費用では解決しない。

**端末の中だけにデータを置く形**

通知の中身を作れないため成立しない(上の表)。加えて機種変更やデータ削除で記録が全部消えるため、6.2 の「何年前でも遡って入力できる」とも噛み合わない。

### この形を選ぶと自動的に決まること

| 項目 | 決まる内容 |
|---|---|
| データの置き場所 | インターネット上に置く |
| 公開 | URLを出す。3.2 の「触れるデモ」の要件を満たせる |
| 自分の使い方 | ホーム画面に追加して使う |

## 14.7.1 要確認事項の調査結果と、候補Dの検討(2026-10-15)

### ログイン機能とアカウントの違い(用語の整理)

| 言葉 | 指すもの |
|---|---|
| アカウント | **1人の利用者を表す登録情報。** 「このメールアドレスの人」という1件のデータ |
| ログイン機能 | **その人が本人だと確かめ、その人のデータだけを見せる仕組み全体。** アカウントを作る、本人か確かめる、他人のデータを見せない、までを含む |

8.2 の「ログイン」は後者を指す。

### Supabase に最初から付いているログイン機能の中身

4つある。

**(1) 本人を確かめる手段**

パスワード、マジックリンク(メールのリンクを押すだけ)、使い捨ての番号(OTP)、他サービスで入る形(Google・Apple・GitHub・Discord・Microsoft など19種類)、電話番号、パスキー、匿名、2段階認証。**どれを選んでも自分で作らずに済む。**

**(2) 利用者の情報を置く場所**

利用者のメールアドレスやパスワードを、Supabase が専用の場所に用意して保管する。**自分で「利用者の表」を作る必要がない。** 13.5 の3つの表に4つ目を足さずに済む。自分の表と結びつけたいときは、記録の表に利用者を指す列を1つ足せば繋がる。

**(3) 通行証(トークン)の発行と管理**

ログインした人には通行証が渡され、データを取りに行くとき自動で一緒に送られる。発行・有効期限の管理・期限切れの更新を Supabase が行う。

**(4) 行単位のアクセス制御(ここが本質)**

表の中の行ごとに「誰が見てよいか」を決める仕組み(Row Level Security)がある。記録の表に「自分が作った行だけ見られる」という決まりを1つ書けば、以降どの画面からデータを取りに行っても他人の記録は返らない。(3) の通行証から「今アクセスしているのは誰か」が分かるため成立する。

**これがない場合に何が起きるか。** データを取るすべての場所で「この人のものだけ取る」条件を自分で書くことになる。**1か所書き忘れると他人の記録が見える。書き忘れても画面は正常に動くので気づかない。**

候補Cの弱点は、この (1)〜(4) の全部を自分で用意することになるという意味である。

### 要確認1:定期実行はできるか → **できる**

**Supabase Cron という仕組みがある。**

| 項目 | 内容 |
|---|---|
| 実行できるもの | SQL、データベースの関数、HTTPリクエスト(Edge Function の呼び出しを含む) |
| 間隔 | 1秒ごとから年1回まで |
| 作り方 | SQL を書くか、管理画面の Integrations → Cron から |
| 中身 | PostgreSQL の pg_cron という拡張機能 |
| 推奨される制限 | 同時に動かすのは8件以下、1件の実行は10分以内 |
| 無料プランで使えるか | **公式ドキュメントにプランの制限の記載がない。** 解説記事では 2026年時点で無料・Pro・Team のすべてで標準で有効とされている |
| 段階 | Beta(試験段階) |

**残る不確かさ(2点)**

1. 無料プランで使えることが公式ドキュメントに明記されていない。解説記事の記述である。**実際にアカウントを作って確かめる必要がある**
2. Beta と書かれている。仕様が変わる可能性がある

**新たに見つかった弱点:失敗しても何も教えてくれない**

- 実行が飛ばされても、やり直されない
- 前の実行が終わっていないと、新しい実行は捨てられる
- 失敗しても通知は来ない。実行履歴に抜けが残るだけ

通知が1日分飛んでも気づけない。**14.6 で「通知は補助、開いた瞬間の画面が本体」と決めた判断は、結果的に正しかった。**

### 要確認2:一時停止は起きるか → **毎日使えば起きない。ただし罠がある**

| 項目 | 内容 |
|---|---|
| 停止の条件 | 直近7日間に十分なデータベースの活動がない場合 |
| 活動とみなされるもの | データベースへのリクエスト。管理画面を開く、アプリから通信が来る |
| 停止を防ぐ目安 | **毎日数回のリクエストがあれば防げる** |
| 警告 | 停止の約1週間前にメールが届く。その後でも活動があれば回避できる |
| 復元 | 停止後1年以内なら管理画面から元に戻せる。データと設定はそのまま |

10.3 で目標にしている使い方そのものが、停止を防ぐ活動になる。

**罠:記録が途切れたときにこそ通知が止まる(重要)**

定期実行は、データベースが正常に動いている間だけ動く。したがって次の流れが成立する。

```

```

**記録が途切れたときにこそ通知が必要なのに、まさにその状況で通知が止まる。** 10.3 の連続日数の目標に対して、1度途切れて放置するとこの仕組みが働く。

| イ | 通知を送る側を Supabase の外に置く。Supabase が止まっていても時計は動き続ける | 構成が複雑になる |

### 要確認4:通知を送る仕組みに何が必要か

Web Push という仕組みを使う。どの候補を選んでも共通して必要。

**(1) 鍵のペア**

公開鍵と秘密鍵という、対になった2つのデータを自分で生成する(VAPID鍵と呼ばれる)。

- 公開鍵:アプリ側に渡す。「この送り主からの通知を受け取る」という紐付けに使う
- 秘密鍵:サーバー側に置く。送信するとき、送り主が本物だと証明するために使う

**(2) 送信先の情報**

アプリ側で通知の許可を取ると、その端末宛ての送信先(URL の形)が発行される。**これをデータベースに保存する必要がある。** 13.5 の3つの表に保存する場所がない。

**(3) 送信する処理**

決まった時刻に動いて、次を行う。

1. データベースから、その日の記録の状況を読む(枠が埋まっているか)
2. 通知の文章を作る
3. 秘密鍵で署名を作る
4. 保存してある送信先に向けて送る

実際に送る部分は既にある部品(web-push というライブラリ)を使える。暗号の処理をゼロから書く必要はない。

**Supabase で組む場合の形**

```
Supabase Cron(決まった時刻に動く)
      ↓ 呼び出す
Edge Function(送信する処理を置く場所)
      ↓ 読む
データベース(記録の状況 + 送信先)
      ↓ 送る
通知が端末に届く
```

Edge Function は Supabase 上で自分の書いた処理を動かせる場所。無料枠は月50万回なので 1日1回なら余裕がある。

**設計への影響:13.5 に表を1つ足す**

通知の送信先を保存する場所がない。ただしこれは 13 の設計を壊すものではない。記録とは別の種類のデータなので、**新しい表を1つ足す形になる。** 9.1 の「既存のデータ構造を壊さずに追加できる設計」が、ここで実際に試される。

## 14.7.2 データの保管場所の決定(2026-10-15)

**Supabase を採用する。**

### 4候補の最終整理

| 候補 | 学習量 | 年内完成への影響 | 費用 | 結果 |
|---|---|---|---|---|
| A. Supabase | 中 | 小さい | 無料 | **採用** |
| B. Firebase | 中 | 小さい | 無料枠あり | 不採用 |
| C. Cloudflare(D1 + Workers) | 大(ログインを自分で作る) | 中 | 無料 | 不採用 |

### 一時停止が実際に起きていた(重要)

**[[my-task-app]] のプロジェクトは、確認した時点で一時停止していた。** 画面に「2027年6月18日まで再開できる」と表示されていた。これは調べた「停止後1年以内なら復元できる」と一致する。

その後、プロジェクトを開いた時点で再開され、現在は稼働中(STATUS は Healthy)。**停止中のプロジェクトは開くと再開される。**

意味することは2つ。

1. **「7日放置で止まる」は実際に起きる。** 推測ではなく実例で確認された
2. **15章 #12 で「my-task-app は現状維持する」と決めていたが、現状維持していたつもりのものは実際には止まっていた**

### 復元してもデータは消えない(確認済み)

公式ドキュメントの記述。

| 項目 | 内容 |
|---|---|
| 復元したとき | 「データや設定を含め、以前の状態に戻る」と明記されている |
| 復元できる期間 | **停止してから1年以内** |
| 手順 | 組織のページ → 停止中のプロジェクトを選ぶ → 「Resume project」を押して確認 |

※ ドキュメント内に「90日」という古い記述の名残があるが、本文は1年。画面の表示(2027年6月18日)も1年と一致するため、1年で正しいと判断した。
※ 1年を過ぎた場合のデータの扱いは公式に記載がない。停止の理由として「バックアップは限られた期間しか保持されない」とだけ書かれている。

### 決定1:一時停止の罠への対処 → **案ア**

**通知は補助とし、開いた瞬間の画面を本体とする。** 通知を Supabase の外に置く案イは採らない。

理由は2つ。

1. **止まっても、管理画面を開けば再開し、データも元通りになる。** 復旧の手段が確実にある
2. 14.6 で既に同じ方針(開いた瞬間の画面が本体)を採っており、2.3 の「外から届くもの1本に頼らない」と一致する

**承知した上で受け入れる不便**

**7日あけてアプリを開いた瞬間は、記録が保存できない。** プロジェクトが止まっているため、アプリ側はエラーになる。管理画面を開いて再開させてから、もう一度アプリを開くことになる。

ただしこれは「7日連続で記録しなかった後」にしか起きない。10.3 の目標通りに使っていれば発生しない。

### 決定2:試作用と本番用を分けるか → **分けない**

**[[my-task-app]] のプロジェクトは残す。** 新しいアプリが2つ目になり、無料枠(2つまで)は埋まる。試作も本番も1つのプロジェクトで行う。

| 選ばなかった案 | 理由 |
|---|---|
| my-task-app のプロジェクトを削除して枠を空ける | 削除するとデータが消える。本人が残すことを選択 |
| 試作は自分のパソコンの中だけで行う | Supabase を自分のパソコンで動かす仕組みを別に覚える必要があり、9.2 に対して重い |

記録を始めるのは試作が終わってからなので、試作中に消して困るデータはまだ存在しない。
