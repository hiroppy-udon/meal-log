## 作るものの全体像

### 画面は3つ

| 画面 | 役目 | 仕様 |
|---|---|---|
| その日の画面 | 入れる・直す。その日を見渡す | 7.5 |
| グラフ | 変化に気づく | 7.6 |
| 全ての記録を見る画面 | 中身を読む | 7.8 |

下部のタブ（今日 / 記録 / グラフ）で行き来する。最初に出るのは「今日」。

### 表は4つ

```
記録の表     id / 日付 / 時刻 / 種類 / 金額 / 備考
食事の表     記録id / 枠 / 自炊か外食か
メニューの表  id / 記録id / メニュー名
送り先の表   id / 送り先 / 登録日時          ← 通知用
```

上の3つが記録、4つ目は通知のためのもので、互いに関係しない。

### 使う技術

| 選ぶ対象 | 決定 |
|---|---|
| 作る形 | ホーム画面に追加して使うWebアプリ |
| データの保管場所 | Supabase |
| 定時実行 | Supabase Cron（pg_cron） |
| 通知の送信処理 | Supabase の Edge Function |
| 画面を作る道具 | React + Vite |
| 公開する場所 | Vercel |

## 実装の最初の3手

11.3 の「最小限を作ってから足す」と、技術選定の手順にある「最も複雑で難しい部分から着手する」に沿う順番。

| 順番 | 内容 | なぜこの順番か |
|---|---|---|
| 1 | **リポジトリを作り、判断の記録を置く** | 11.1。判断の記録はコードと一緒に管理する。今が最も書きやすい |
| 2 | **通知が実際に届くかを先に試す** | **最も難しい部分から着手する。** iPhone でWebアプリの通知は止まる場合があるという報告が本当かどうかは、試さないと分からない。**ここが崩れると 7.1 の機能が1つ消える** |
| 3 | **その日の画面（7.5）を作る** | 12.5 で「最初に出るのは今日の画面」と決めている。記録と振り返りの土台 |

2を先にやる理由は、**後半で「要件を満たせない」と分かるのを防ぐため**である。画面を先に作り込んでから通知が動かないと分かると、作り直しになる。

## 実機で確認済みのこと

Supabase のダッシュボードで実際に確認した（2026-10-15）。設定の変更は行っていない。

| 項目 | 確認結果 |
|---|---|
| プラン | hiroppy-udon's Org、FREE |
| **pg_cron** | 拡張機能の一覧にある（version 1.6.4）。ENABLED はオフ。**無料プランで定時実行が使える** |
| **Edge Functions** | 無料枠に月50万回含まれる |
| **Authentication** | ログイン方法が最初から並ぶ。Email はオン済み |
| プロジェクト数 | 1個（my-task-app のもの）。新規が2つ目になり枠が埋まる |

**一時停止が実際に起きていた。** my-task-app のプロジェクトは確認した時点で一時停止しており、「2027年6月18日まで再開できる」と表示されていた。開いた時点で再開され、現在は稼働中。

→ 「7日放置で止まる」は推測ではなく実例で確認された。
