# 第2部 何を作るのか

## 4. 目的

目的は3つの層に分かれている。混同しないこと。

### 4.1 一番の目的

**エンジニア職に応募するときのポートフォリオ。および、それを作る過程での学習。**

### 4.2 実際に解決したいこと(題材)

**お金と健康の管理。** やりたいことは次の3つ。

1. **今日の食事・出費を記録する**(ゆくゆくは睡眠時間、やることなど生活全般へ広げる)
2. **月ごと、あるいは一週間の記録を確認する**
3. **記録を振り返って生活習慣を見直し、リズムを整え、次の週に活かす**

確認したい内容は2つ。

- **無駄なく抑えられているか**(お金の面)
- **安定した食事がとれているか**(食事の面)

**記録した先にあるもの(重要):** 記録することが目的ではない。**週という単位で振り返り、次の週の行動を変える**という流れを回すことが目的。したがって振り返りの画面は「見て終わり」ではなく、次の週の判断材料になる形である必要がある。

### 4.3 満たすべき条件

**利用頻度が高いこと。**

前のアプリ(my-task-app)は使う頻度が低く、使われなくなった。自分がよく触るプロダクトは「刺激がある」か「利用頻度が高い」かのどちらかであり、このアプリは後者を目指す。記録するタイプのアプリは、触る機会が多いほど習慣の一部に溶け込む。

ただし**これは目的ではなく、4.1 と 4.2 を達成するために満たすべき条件**である。使われていないプロダクトでは、ポートフォリオに載せる成果の数字(10)が出せない。

### 4.4 なぜ既存のアプリでなく自分で作るのか

順序に注意すること。

```
ポートフォリオが必要
  → 題材を何にするか
  → 自分が実際に困っていて、かつ毎日発生するものがいい
  → 記録の課題(レシートアプリやスプレッドシートの使いにくさ)を選んだ
```

レシートアプリへの不満は、**アプリを作る理由ではなく、題材を選ぶときの基準**である。

したがって「既存の家計簿アプリを使えば済むのでは」という問いへの答えは、「既存アプリを使ってもポートフォリオにはならない」になる。実用面の課題を解決するだけなら、既存アプリで足りる。

## 5. 使う場面

```
1日の終わり、帰宅した後
  → 落ち着いている、両手が空いている
  → その日の食事と買い物をまとめて入力する
  → 1日1回の操作
```

**この場面から決まること**

| 項目 | どうなるか |
|---|---|
| 極端にタップ数を減らすこと | 不要。落ち着いた状況なので数十秒かけられる |
| 1日分をまとめて入力する画面 | 必要 |
| 過去に遡って入力するための専用の画面 | 不要。日付の欄が編集できれば足りる |
| 通知 | **重要度が高い**。1日1回の操作なので、1回逃すと1日分が丸ごと抜ける |

## 6. 記録する内容

### 6.1 1日の形 — 枠という考え方

**1日には決まった枠がある。並びはもともと決まっているので、時間順に並べ替える必要がない。**

```
起床 → 朝 → 昼 → 晩 → 間食 → 入眠
```

この並びがそのまま1日の形になる。毎日同じ形で固定する。

> 理由: 枠の並びが1日の形そのものなので、並べ替える仕組みが要らない。この捉え方が 7.5 と 7.8 の画面の形を決めている（判断の記録 #19）

**枠ごとに記録する内容**

| 枠 | 時刻 | 自炊か外食か | メニュー | 金額 | 備考 |
|---|---|---|---|---|---|
| 起床 | 必要 | — | — | — | 任意 |
| 朝・昼・晩・間食 | 必要 | 自炊 / 外食 / なし | 複数可 | 外食のときのみ | 任意(店名など) |
| 入眠 | 必要 | — | — | — | 任意 |

**枠に入らないもの:買い物**

買い物は1日の流れの中に位置を持たない。**時刻は記録しない。**

| | 金額 | 中身 |
|---|---|---|
| 食材の買い物 | 必要(合計のみ) | 備考欄に文章で書く(13.6) |

**支払い方法は記録しない**

> 理由: 元の課題は「記録が漏れること」であり、支払い方法そのものを記録したい話ではなかった。手で記録する仕組みを作った時点で解決している。必要になれば後から足せる（判断の記録 #20）

### 6.2 全部に共通する決まり

- 日付は自由に指定できる。**何年前でも遡って入力できる**(そのための専用の画面は作らない)
- **日付の行はアプリ側が用意する。使う人が記録を置く場所を作る作業をゼロにする**(理由は 10.2)
- 全ての記録に備考欄(自由に書ける)を付ける
- 記録を直せる、消せる
- 金額と食事内容はどちらも任意。片方だけでも保存できる
- **記録していない日と、0円・0件の日を区別する。** 食べなかった時間帯には「**なし**」という選択肢を選んで記録する(これで「記録し忘れ」と「食べなかった」が区別できる。7.4 の数え方の前提になる)
- **時刻は分単位で記録する。** 起床・朝・昼・晩・間食・入眠のすべて。この時刻のばらつきが、生活リズムを測る材料になる(7.7)
- **1回の食事に複数のメニューを登録できる**

### 6.3 食事の時間帯の呼び方

朝 / 昼 / 晩 / **間食** の4つ。

> 理由: 当初この4つ目は「その他」だったが、記録の種類にも「その他」があり、別の軸を指す同じ言葉が2か所に出て混同した。時間帯の方を「間食」に変えて解消した（判断の記録 #13）

時間帯は「いつ食べたか」、記録の種類は「何をしたか」を表す別の軸である。間食をコンビニで買って食べれば、時間帯は「間食」で種類は「外食」になる。

## 7. 画面に出すもの

### 7.1 最小限の機能

1. 支出の記録
2. 食事の記録
3. 記録を直す・消す
4. 一覧と振り返り(中身は 7.2)
5. 通知(記録の状況を見せる)
6. **ログイン**(7.9)

### 7.2 振り返りに出すもの

| 面 | 出すもの |
|---|---|
| 出費 | **期間ごとの食費の合計を、棒グラフで並べて見せる**(詳しくは 7.6) |
| 食事 | **日ごとに枠が並び、時刻・自炊か外食か・メニューが読める**(形は 7.8) |
| 食事の安定 | **自炊と外食の比率 / 食事時刻のばらつき**(詳しくは 7.7) |
| 続き具合 | **記録日数を3つの数字で出す** — 累計 / 今月 / 連続(最高記録つき)。完了した日の判定は 7.4、3つの数字の詳細は 10.3 |

**どこまで見せるか**

- **直近1週間**: 何も押さなくても中身が見える
- **それ以前**: 範囲を切り替えれば、全ての記録を見られる(7.8)

### 7.3 振り返りの単位

- 振り返りは**日・週・月で切り替えられる**(日は 7.6 のグラフで追加)
- 基本で表示するのは「**今週**」「**今月**」
- 「**先週**」「**先月**」も選べる

画面は3つ。内訳は 12.4 にある。

### 7.4 記録日数の数え方

**アプリ側で自動的に判定する。「今日は終わり」のようなボタンは作らない。**

```
朝・昼・晩・間食の4つの時間帯すべてに記録がある日 = その日は完了 → 記録日数に数える
  ※「なし」も記録の一種として数える
1つでも記録していない時間帯がある日 = 未完了
```

**なぜこれで判定できるか:** 食べなかった時間帯には「**なし**」を選んで記録する(6.2)。欠食が「記録がない状態」ではなく「なしという記録がある状態」になるため、記録し忘れと区別できる。判定に必要な情報が存在するので、自動で判定できる。

**買い物について:** 時間帯に属さない記録なので、完了の判定には関係しない(買い物をしなかった日も、4つの時間帯が埋まっていれば完了)。

→ 「この日は完了した」という印をデータに持つ必要はない。4つの時間帯が埋まっているかを記録から計算すればよい。

### 7.5 その日の画面

1日の枠(6.1)をそのまま並べる。**記録を見る場所であり、入れる場所でもある。**

```
10月13日(月)

 起床    7:05
 ──────────────────────────────────
  朝     8:12   自炊   目玉焼き、味噌汁
  昼    12:40   外食   ラーメン、餃子       ¥900
  晩    19:30   自炊   カレー
  間食    ―      ―      ―
 ──────────────────────────────────
 入眠   23:40

 買い物   スーパー                        ¥2,340
 この日の出費                             ¥3,240
```

- 起床と入眠が食事の枠を挟む。これが1日の形
- **買い物は枠の外。時刻は出さない**
- その日の出費の合計も枠の外

**入力の仕方:Excel のように、押したところに直接打つ**

別の画面に移らない。下からせり上がる入力欄も出さない。**押したセルにその場で打つ。**

- 自炊か外食かの欄を押す → 自炊 / 外食 / なし の選択肢が出る
- 時刻の欄を押す → 時刻の選び方が出る
- メニューの欄を押す → そのまま文字が打てる

> 理由: 画面を移る必要がなく、その場で打てれば足りる。この形にしたことで入力専用の画面が不要になった（判断の記録 #22）

**記録していない枠と「なし」は別の見た目にする**

記録していない枠は空欄、食べなかった枠は「なし」。6.2 で区別すると決めているので、画面でも分ける。

**備考をどこに置くか**

横幅に入らないため、**行の右端に小さな印を置き、押すと備考だけが開く**形にする。備考を書く日は少ないので、普段は邪魔にならない。

### 7.6 推移を見るグラフの画面

**この画面が「変化を見る」役目をすべて引き受ける。**

#### 今回作る範囲

**生活習慣における出費の動向を見える化すること。** これに絞る。

起床・入眠・食事の時刻をグラフにするのは、今回は作らない。ただし**後から足せる形を想定して作る。**

> 理由: 時刻は「量」ではなく「時点」なので、棒の高さで表しても読めない。グラフの形そのものを変える必要があり、今回の範囲では重すぎる（判断の記録 #27）

#### この画面が答える問い(重要)

**合計の出費が実際に減っているか。変動はどうなっているか。それを確かめて次につなげる。**

→ **外食を減らすことが目的ではない。** 重要なのは合計の出費である。

7.7 で「自炊と外食の比率」を見ると決めているが、あれは**健康の面**(安定した食事がとれているか)の材料であって、お金の面の材料ではない。4.2 の2つの目的のうち、どちらに属するかを混同しないこと。

| 目的 | 見るもの | どこで見るか |
|---|---|---|
| 無駄なく抑えられているか(お金) | **合計の出費と、その変動** | この画面(7.6) |
| 安定した食事がとれているか(健康) | 自炊と外食の比率、食事時刻のばらつき | 7.7 |

#### 画面の中身

```
 出費の動向

 [ 日 ]  [ 週 ]  [ 月 ]          ← 期間の単位

 ◀  2026年  ▶                    ← 年の切り替え

        ┌──────────────┐
        │  9月    ¥16,756   ▶│   ← 選んだ期間
        └──────────────┘

  (万)
   2 ┤                █
   1 ┤   █ █ █   █ █  █  █
   0 └──────────────────
     1月 2月 3月 ... 9月 10月

 ──────────────────────
  この期間の記録を見る   →        ← 7.8 へ移動
```

| 項目 | 内容 | 理由 |
|---|---|---|
| 見出し | **「出費の動向」** | 下記の育ち方を採るため |
| 平均 | **出さない** | 数字で出されても判断の材料にならない。並べて見れば分かる（判断の記録 #28） |
| 日を選んだときに並べる本数 | **その月の日数分** | 月の切り替えと動きが揃う。日は月を切り替え、週と月は年を切り替える（判断の記録 #29） |
| 選んだ棒 | 色を濃くし、上に金額を大きく出す | 参考にした銀行アプリの画面と同じ |

**なぜ数字の比較ではなくグラフなのか**

> 理由: 「平均より +4,200円」のような差を数字で出されても判断の材料にならない。並べて見たときに初めて「この月は多い」と分かる。4.2 の「極端に多い月を見返して備考欄を読み、次に活かす」という使い方は、グラフがないと成立しない（判断の記録 #15）

#### 出費の種類が増えたときの育ち方

将来、交通費やサブスクを記録するようになったときの形。

**「出費」という1つの場所があり、中で種類を切り替える。**

```
[ 出費 ]  [ 起床 ]  [ 入眠 ]       ← 何を見るか(上の段)
   └ [ 全部 ] [ 食費 ] [ 交通費 ]   ← どの出費か(下の段)
```

理由は2つ。

1. 項目が横に増え続けない。出費の種類が10個になっても、上の段は「出費」のまま
2. **「全部でいくら使ったか」が見られる。** 種類ごとにグラフを並べる形だと、食費と交通費を足す場所がない。合計の出費こそが重要なので、これが決め手になった（判断の記録 #30）

今は出費の種類が食事関係しかないので、**どちらの段の切り替えも画面に出ない。** 種類が増えたときに現れる。

#### 将来の姿

最終的に「タスクや生活習慣全般を一括管理する」という目標からすると、**この画面が一番伸びる。** 数値になるものはすべてここに乗る。

| 見るもの | 数値の性質 | 合う形 | 今回作るか |
|---|---|---|---|
| **出費(食費)** | **量。足し算できる** | **棒グラフ** | **作る** |
| 起床・入眠・食事の時刻 | 時点。1日の中の位置 | 横軸に24時間を取った形 | 作らない |
| 睡眠時間 | 量(長さ) | 棒グラフ | 作らない |
| タスクの消化 | 量または割合 | 棒グラフ | 作らない |

**時刻を見せるときの形(将来の想定)**

```
       0    3    6    9   12   15   18   21   24
 10/13 ─────────◇──□──────△────────○──────●───
 10/12 ─●───────────◇─□─────△─────────○──────
 10/11 ─────────◇□───────△──────○────●───────

   ◇起床  □朝  △昼  ○晩  ●入眠
```

1行が1日。横軸が24時間。印が左右に動くことで、リズムのずれが見える。**この形に変えることを想定して作る。**

項目を足すときに画面をどう構成するかは、足すときに決める(進行状況.md の未決定)。

#### 設計への影響(2つ)

1. **画面を3つ作る必要はない。1つの画面で単位を切り替えればよい。**
   日・週・月は集計する単位が違うだけで、出すもの(期間ごとの食費合計)は同じ。画面を分ける理由がない。

2. **この画面が「一覧」、その先が「詳細」になる。**
   棒を選んでその期間の明細へ移動する流れは、オブジェクト指向UI(12.2)の「一覧から選んで詳細を見る」そのもの。

#### 作る順番

時間がかかりすぎるのを防ぐため、段階的に作る(11.3 の方針に沿う)。

1. まず**金額だけの表**を作る(期間と合計金額が並ぶだけ)
2. その後グラフに置き換える

### 7.7 食事が安定しているかの見方

4.2 の「安定した食事がとれているか」を、**栄養素を見積もらずに判断する。**

> 理由: 栄養素の見積もりは入力の手間が大きく、続かない。既に記録すると決めている情報だけから計算できる数字を使う（判断の記録 #18）

**採用する2つ**

| 数字 | 何から計算するか | 追加の入力 |
|---|---|---|
| **自炊と外食の比率** | 記録の種類(6.1)を数える | なし |
| **食事時刻のばらつき** | 分単位で記録している時刻(6.2) | なし |

**食事時刻のばらつきを使う理由(3つ)**

1. 4.2 の目的に「リズムを整える」と書いてある。時刻のばらつきは、リズムそのものを測る数字になる
2. 6.2 で「食事の時刻は分単位で記録する」と決めていたが、それが何に使われるかは曖昧なままだった。ここで役割がつく
3. **睡眠の記録を足さなくても、今の仕組みだけでリズムが測れる**

**出し方のイメージ**

```
今週の食事
  自炊 14回 / 外食 5回
  朝食の時刻  7:40 〜 10:20（ばらつき 2時間40分）
  夕食の時刻  18:50 〜 19:30（ばらつき 40分）
```

朝食の時刻が毎日2時間以上ずれているなら、それだけで「リズムが崩れている」と分かる。何を食べたかを分析する必要がない。

**今は使わないもの**

欠食の回数、食事の間隔、外食が続いた日数、よく食べるメニュー。追加入力なしで計算できるが、今回は出さない。記録は残るので必要になったら足せる。

### 7.8 全ての記録を見る画面

**その日の画面(7.5)を縦に連ねた形にする。**

```
 10/13(月)                          ¥3,240
   起床  7:05                  入眠 23:40
   朝   8:12   自炊   目玉焼き、味噌汁
   昼  12:40   外食   ラーメン、餃子
   晩  19:30   自炊   カレー
   間食  ―

 10/12(日)                              ―
   起床  9:30                  入眠  1:20
   朝  10:15   自炊   トースト
   ...
```

範囲を切り替えられる(直近1週間 / 1ヶ月 / 全期間)。

**それとは別に、外から期間を指定して開ける必要がある。** グラフ(7.6)で9月を選んで移動したとき、9月を表示した状態で開かなければならない(12.5)。

> 理由: 表の形（日を縦・枠を横）は却下した。時刻の数字だけでは見る気が起きず、自炊か外食か・記録したかどうかが分からないため。変化を見る役目はグラフ(7.6)が持つので、表の形にする必要がない（判断の記録 #23、#24）

**この形の利点**

**日の一覧と全ての記録を見る画面が、1つで済む。** 7.2 で「日ごとに4つの枠で自炊か外食かが分かる」と決めていた画面と、全ての記録を見る画面が、範囲の違いだけになる。

12.3 のオブジェクト指向UIでは「要らない画面は省いて数を抑える」とされている。これに沿う。

**役目の分担**

| やりたいこと | どの画面 |
|---|---|
| **変化に気づく** | グラフ(7.6) |
| **中身を読む** | 全ての記録を見る画面(7.8) |
| **入れる・直す** | その日の画面(7.5) |

> 日の一覧をカレンダーにする案は却下した。カレンダーが速いのは「特定の日を探す」ときだが、実際の使い方は「最近の食生活を振り返る」ことが多いため（判断の記録 #26）

### 7.9 ログイン

**メールアドレスとパスワードで入る。自分1人が使う。**

#### なぜ必要なのか

Webアプリは、データベースに繋ぐための鍵をブラウザの中に持つ。**この鍵は公開される前提のもの**で、守っているのは鍵ではなく、データベース側の「行単位のアクセス制御」である。

この仕組みを設定しないまま公開すると、**URLを知っている人は誰でも記録を読めて、書き換えられて、消せる。** 10.3 の記録日数も消える。

そして、この仕組みは「誰がアクセスしているか」を条件に書く。**ログインがないとその材料が存在しない。**

```
ログインがない  → 誰がアクセスしているか分からない
               → 「自分の行だけ」という条件が書けない
               → 全部読める / 全部書ける
```

3.2 で「採用担当者が触れる公開URLを出す」と決めている以上、ログインは避けられない。

#### 画面

```
 メールアドレス  [                    ]
 パスワード      [                    ]

          [ ログイン ]
```

ログインしていない状態では、この画面だけが出る。

#### データ側の決まり

4つの表すべてに、**自分が作った行だけを読み書きできる**決まりを設定する。

| 表 | 決まり |
|---|---|
| 記録の表 | 自分の行だけ |
| 食事の表 | 自分の記録に紐づく行だけ |
| メニューの表 | 自分の記録に紐づく行だけ |
| 送り先の表 | 自分の行だけ |

記録の表と送り先の表に、**利用者を指す列を1つ足す**。13.5 で「複数人での利用を足すときは1列足すだけ」と設計していたものを、前倒しで使う。

#### 作らないもの

| 作らないもの | 理由 |
|---|---|
| 新規登録の画面 | 使うのは自分1人。管理画面から1件作れば足りる |
| パスワードを忘れたときの画面 | 同上。必要になったら足せる |
| 他のサービスで入る形（Googleなど） | メールアドレスで足りる。選択肢は後から増やせる |
| 匿名で入る形 | **誰でもログイン済みになるため、アクセス制御の意味がなくなる** |

## 10. うまくいったかの測り方

### 10.1 前の状態

**既存の Google スプレッドシートによる記録は、1ヶ月続いて、やめた。**

### 10.2 やめた理由 — 要件に反映済み

スプレッドシートでは、記録するたびに自分で行を足し、日付を書き、書式を整える必要があった。**記録そのものではなく「記録を置く場所を自分で用意する作業」が面倒だった。**

また「シートを作ったとき、ここまで続くと思っていなかった」ため、長く続けることを前提にした作りになっていなかった。

→ 6.2 の「日付の行はアプリ側が用意する」および 9.1「拡張に耐える設計」に反映済み。

### 10.3 目標

前の状態が「1ヶ月続いてやめた」なので、それと比べられる数字にする必要がある。

**使う数字は3つ**

| 数字 | 何が分かるか |
|---|---|
| **累計の記録日数** | 全体でどれだけ記録してきたか。減らない |
| **月あたりの記録日数** | その月の密度。「一応続いているが中身がない」状態を見つけられる |
| **連続日数(最高記録つき)** | 今の勢いと、これまでの最高 |

**画面での出し方**

```
記録日数   累計   87日
          今月   24日 / 31日
          連続   12日（最高 24日）
```

**なぜ連続日数に最高記録を付けるのか**

連続日数を素直に出すと、1日忘れた翌日に「連続 0日」と表示され、積み上げがゼロに戻って再開する気がなくなる。**最高記録を併記すれば、連続が0に戻っても「24日続けられた」という事実は画面に残る。**

> 連続日数はアプリ内で見せる数字であり、プロジェクトの成否を測る主な指標ではない（判断の記録 #6、#17）

**計算方法**

4つとも記録から計算できる。データに別の印を持つ必要はない(7.4 と同じ結論)。

| 数字 | 計算方法 |
|---|---|
| 累計の記録日数 | 完了した日(7.4)の総数 |
| 月あたりの記録日数 | その月に完了した日数 ÷ その月の日数 |
| 連続日数 | 今日から遡って、連続して完了している日数 |
| 最高の連続日数 | 過去の全記録から、連続して完了した最長の日数 |

### 10.4 前のアプリの見せ方から得た教訓

前のアプリ(my-task-app)では、記録の状況をマス目で見せていた。マス目を押すと日付とその日に達成したかが出る形。**この形は分かりにくかった。**

→ **記録日数は、数字そのものをはっきり出す。** マス目で見せるだけにしない。

# 第3部 どう作るのか

## 11. 進め方の決まりごと

### 11.1 決めたことを記録に残す(ADR)

ADR は Architecture Decision Record の略で、設計上の選択を記録したもの。何かを決めたとき、その判断理由を短いテキストにまとめる。

- **書く内容:** 題名、背景、決めたこと、今の状態、結果、検討した候補、判断の基準、候補同士の比較
- **置く場所:** ソースコードと一緒にリポジトリの中で管理する(コードと記録が同期する)
- **書く対象:** 候補が複数あり、後から見て判断理由が推測しにくいもの

**採用した理由:** README に「選ばなかった候補も書く」という項目があり、それと完全に一致する。アプリ自体が仮説を検証する手段でもあるため、後から「この判断が効いた・外した」を振り返る必要がある。

→ ここまでに決めたことは『判断の記録.md』にある。

### 11.2 参考にした他のやり方

| やり方 | 内容 | 本件での扱い |
|---|---|---|
| ユーザーストーリー | 「<だれ>として、<何か>をしたい。それは<理由>だからだ」の形で要求を書く | 考え方を参照 |
| ユースケース記述 | 操作の手順や例外の扱いまで含めて「どう動くか」を書く | 5 で実施済み |
| MVP開発 | 需要があるか分からない製品を最小限だけ作り、反応を見て確かめる | **該当しない**。使う人は自分で、需要は分かっている |

### 11.3 作る順番の方針

**最小限の機能を作ってから、後で機能を足したり直したりする。**

> 理由: 9.1 の「今あるデータの構造を壊さずに新しい記録の種類を足せること」と一致するため（判断の記録 #8）

#### 前回の失敗との違い(重要)

前回(my-task-app)の失敗の原因は「要件が決まっていなかった」ことだった。この方針はそれと似て見えるが別物。

- 前回: 要件を決めないまま作った
- 今回: **作る範囲を最小限に絞り、その範囲の要件は細かく決める。範囲の外は意図的に保留する**

**保留が「忘れていた」ではなく「意図的に外した」になっているかが分かれ目。** 8.1 の「今回は作らないもの」の一覧がその役割を持つ。範囲の外のものを足すときは、その都度 第2部 と同じ細かさで要件を決めてから着手すること。

### 11.4 作る資料

機能一覧 → **画面のつながりの図** → **画面の中身の配置** → **試作** の4つを作る。

配色や書体を決める資料と、機器や通信の配置を決める資料は、今回は作らない。

> 進捗は『進行状況.md』にある。

## 12. 画面の組み立て方

### 12.1 2つの考え方

| 考え方 | 操作の順序 | 例 |
|---|---|---|
| タスク指向UI | 先に「やること」、後から「対象」 | メールソフトで「新規作成」を押してから宛先を入力する |
| **オブジェクト指向UI** | **先に「対象」、後から「やること」** | メッセージアプリで相手を選んでから送信する |

※ ここでいう「オブジェクト」は、画面の上で使う人が扱う対象物のこと。プログラミングのオブジェクト指向とは別の話。

### 12.2 採用した考え方と理由

**オブジェクト指向UIを採用する。**

理由は3つ。

1. 単純なアプリにする予定がない。やることの種類が増えるほど、タスク指向UIは目的にたどり着きにくくなる
2. 融通の利く設計にして後から機能を足したり直したりできる構造が求められる。対象を起点にすると画面の数が減り、プログラムも単純になる
3. 8.2 の「あとで足すもの」(起床・就寝・掃除・運動)と相性がよい。タスク指向だと「起床を記録する」「掃除を記録する」とメニューが増え続けるが、オブジェクト指向UIなら「日」という対象の下に枠が増えるだけで、画面の構造は変わらない

（判断の記録 #11）

### 12.3 作り方の手順

1. **画面で扱う対象を洗い出す** — やりたいことに出てくる名詞を書き出し、重要なものに絞る
2. **画面を2種類に分けて置く** — 一覧を見せる画面と、1件の詳細を見せる画面。この2つの行き来の仕方を図にする。要らない画面は省いて数を抑える
3. **画面の中身を配置する** — 画面の大きさに合わせて置く。置いた後に1〜3を行き来して直す

**手順1の結果:** 扱う対象は次の3つ。

| 対象 | 根拠 |
|---|---|
| 日 | 13.3 の全ての記録が「日付」を共通して持つ |
| 記録 | 13.3 の各行(外食・自炊・買い物、あとで起床・就寝・掃除・運動) |
| メニュー | 13.2、13.3(1回の食事に複数ぶら下がる) |

### 12.4 画面の一覧

| 対象 | 一覧 | 1件 |
|---|---|---|
| 日 | 全ての記録を見る画面(7.8)。範囲を切り替えられる | その日の画面(7.5) |
| 期間(日/週/月) | グラフ(7.6) | その期間の記録 → 7.8 へ |
| 記録 | 作らない。日の中に収まる | 作らない。その場で打つ(7.5) |
| メニュー | 作らない | 作らない |

**画面は3つ。入力専用の画面は作らない。**

> 理由: その日の画面(7.5)が、見る場所と入れる場所を兼ねる。押したところに直接打つ形にしたため、入力専用の画面が要らない。「出費と食事を分けて見たい」という要求は、画面を分けるのではなく役目を分ける形で満たした（判断の記録 #5、#22）

### 12.5 画面の行き来

#### 2つの流れ

```
【毎日】
 アプリを開く → その日の画面(7.5) → 記録を入れる

【ときどき】
 グラフ(7.6)
   │  変化が激しい日・月を見つける
   ↓  その棒を選んで「この期間の記録を見る」
 全ての記録を見る画面(7.8)
   │  選んだ期間を表示した状態で開く。備考を読む
   ↓  日を選ぶ
 その日の画面(7.5)
```

#### 下部のタブで行き来する

```
 ┌──────────────────────┐
 │                            │
 │        画面の中身           │
 │                            │
 ├──────────────────────┤
 │   今日    記録     グラフ    │
 └──────────────────────┘
```

| タブ | 開く画面 | いつ使うか |
|---|---|---|
| **今日** | その日の画面(7.5) | 毎日。記録を入れる |
| 記録 | 全ての記録を見る画面(7.8) | 振り返るとき |
| グラフ | グラフ(7.6) | 変化を見るとき |

**最初に出るのは「今日」。** 4.3 の最優先条件が「利用頻度が高いこと」であり、毎日やることは記録だから。開いた瞬間に記録できる状態にあるのが、一番摩擦が少ない。（判断の記録 #31）

#### ここから出てくる作り方の条件

**全ての記録を見る画面(7.8)は、外から期間を指定して開ける必要がある。**

グラフで9月を選んで移動したとき、7.8 が最新の記録から始まっていては意味がない。9月を表示した状態で開かなければならない。

7.8 は範囲を切り替えられる形(直近1週間 / 1ヶ月 / 全期間)だが、それとは別に、**特定の期間を指定して開く入口**が要る。

## 13. データの持ち方

### 13.1 前提にしている知識

- 表は行と列からできている
- 複数の表を関連付けるには、各行に重複しない番号を振り、相手の表からその番号を参照する(13.2)

### 13.2 表を分けて結びつける方法

表の全体を指すのでは足りず、**その表のどの行を指すか**を特定する必要がある。各行に重複しない番号を振り、相手の表にその番号を書く。

**食事の表**

| 番号 | 日付 | 時間帯 | 時刻 | 種類 |
|---|---|---|---|---|
| 1 | 10/3 | 晩 | 19:30 | 外食 |
| 2 | 10/3 | 朝 | 8:00 | 自炊 |

**メニューの表**

| 番号 | どの食事か | メニュー名 |
|---|---|---|
| 1 | 1 | ラーメン |
| 2 | 1 | 餃子 |
| 3 | 2 | 目玉焼き |

これで「1回の食事に複数のメニュー」が、メニューの表に行を足すだけで表せる。

> 1つの表に `メニュー1`〜`メニュー3` と列を並べる形は採らない。4品食べた日に列を足す必要があり、ほとんどの行が空欄になり、集計も難しくなるため

### 13.3 データは2種類に分かれる

**これが設計の軸になる。**

| | 1つの記録につき | 例 |
|---|---|---|
| **単一のもの** | 必ず1つ | 時刻、自炊か外食か、金額、備考 |
| **複数ぶら下がるもの** | 0個から何個でも | メニュー、掃除の場所、タスク |

単一のものは表の列にできる。複数のものは列にできない。

#### 記録の種類ごとの中身

| 記録 | 日付 | 時刻 | 単一のもの | 複数ぶら下がるもの |
|---|---|---|---|---|
| 起床 | あり | あり | — | — |
| 入眠 | あり | あり | — | — |
| 食事 | あり | あり | 枠(朝/昼/晩/間食)、自炊か外食か、金額(外食のみ) | メニュー |
| 買い物 | あり | **なし** | 金額 | — |
| (将来)掃除 | あり | あり | — | 場所 |
| (将来)運動 | あり | あり | 時間 | 種目 |
| (将来)タスク | あり | ? | 未定 | 未定 |

**共通するのは「日付」と「何の記録か」。時刻もほぼ共通(買い物だけない)。それ以外は種類ごとにばらばら。**

### 13.4 採用した形

**共通の表1つ + 種類ごとの表。**

> 検討した案は3つあり、「1つの表に全ての列を置く」形は、外部から指摘された失敗例そのものだったため除外した。「種類ごとに表を完全に分ける」形は、1日の全記録を集めるのが重くなる（判断の記録 #7）

### 13.5 表の形

```
記録の表
  id / 利用者 / 日付 / 時刻 / 種類 / 金額 / 備考

食事の表
  記録id / 枠 / 自炊か外食か

メニューの表
  id / 記録id / メニュー名
```

食事の表とメニューの表には利用者の列を置かない。**記録idを辿れば誰のものか分かる**ため、同じ情報を2か所に持たない。

#### 各列を置いた理由

**記録の表**

| 列 | 理由 |
|---|---|
| id | 他の表から指すため(13.2) |
| **利用者** | **誰の記録か。7.9 のアクセス制御がこの列を使う** |
| 日付 | すべての記録が持つ |
| 時刻 | 起床・入眠・食事が持つ。買い物は空欄(6.1 で時刻を記録しないと決めた) |
| 種類 | 起床 / 入眠 / 食事 / 買い物 |
| 金額 | 外食と買い物が持つ。**7.6 の出費合計を、この列を足すだけで出すため**（判断の記録 #32） |
| 備考 | すべてに付ける(6.2)。買い物の中身もここ(13.6) |

**食事の表**

| 列 | 理由 |
|---|---|
| 記録id | どの記録のものか |
| 枠 | 朝 / 昼 / 晩 / 間食。7.4 の完了判定に使う |
| 自炊か外食か | 自炊 / 外食 / なし。7.7 の比率に使う |

**メニューの表**

| 列 | 理由 |
|---|---|
| id | 1行を特定して消すため |
| 記録id | どの食事のものか |
| メニュー名 | 名前だけ |

#### 実際にデータを入れた例(10月13日)

**記録の表**

| id | 利用者 | 日付 | 時刻 | 種類 | 金額 | 備考 |
|---|---|---|---|---|---|---|
| 1 | hiro | 10/13 | 7:05 | 起床 | | |
| 2 | hiro | 10/13 | 8:12 | 食事 | | |
| 3 | hiro | 10/13 | 12:40 | 食事 | 900 | 二郎系 |
| 4 | hiro | 10/13 | 19:30 | 食事 | | |
| 5 | hiro | 10/13 | | 食事 | | |
| 6 | hiro | 10/13 | | 買い物 | 2340 | 鶏むね肉、キャベツ、米5kg |
| 7 | hiro | 10/13 | 23:40 | 入眠 | | |

利用者の欄は、実際には人が読める名前ではなく、ログインした人に割り振られる番号が入る。ここでは分かりやすさのため `hiro` と書いている。

**食事の表**

| 記録id | 枠 | 自炊か外食か |
|---|---|---|
| 2 | 朝 | 自炊 |
| 3 | 昼 | 外食 |
| 4 | 晩 | 自炊 |
| 5 | 間食 | なし |

**メニューの表**

| id | 記録id | メニュー名 |
|---|---|---|
| 1 | 2 | 目玉焼き |
| 2 | 2 | 味噌汁 |
| 3 | 3 | ラーメン |
| 4 | 3 | 餃子 |
| 5 | 4 | カレー |

id=5 は間食の「なし」。食べていないので時刻も金額もない。これは**意味のある空欄**である。

#### 複数ぶら下がるものは、種類ごとに別の表にする

将来、メニュー・掃除の場所・タスクが同じ形で現れる。**それぞれ別の表を作る。**

> 理由: タスクは名前だけで済まない可能性が高い（終わったかどうか、いつまでにやるか）。1つの表にまとめた後でタスクだけ列が必要になると、その列はメニューの行にも掃除場所の行にもできてしまう。**分かれているものをまとめるのは簡単だが、まとめたものを分けるのは、既に入っているデータを動かす必要がある**（判断の記録 #33）

#### 将来足すときに何が起きるか

| 足すもの | やること | 記録の表を触るか |
|---|---|---|
| 掃除 | 種類に「掃除」を足す。掃除場所の表を1つ作る | 触らない |
| 運動 | 種類に「運動」を足す。運動の表を1つ作る | 触らない |
| タスク | 種類に「タスク」を足す。タスクの表を1つ作る | 触らない |
| 交通費など別の出費 | 種類を足す。金額は既にある列を使う | 触らない |
| 他人を招いて一緒に使う | 招待の仕組みと、共有の決まりを作る | **触らない。利用者の列は既にある** |

利用者の列は 7.9 のログインのために既に置いてあるため、**他人と一緒に使う形にするときも、記録の表に手を入れる必要がない。**

#### 置かないもの

| 置かないもの | 理由 |
|---|---|
| 記録の種類「その他」 | 何でも入る箱を作ると、本来は新しい種類として足すべきものがそこに溜まり、後から分けられなくなる。種類はいつでも足せる形になっている（判断の記録 #34） |
| 「日」の表 | 日付は記録の表が持っている。完了したかは食事の表から計算できる(7.4)。将来「その日のひとこと」を書きたくなったら作る（判断の記録 #35） |

### 13.6 買い物の中身をどう持つか

**1つの文章(文字列)として備考欄に持つ。品物ごとに行を分けない。**

食事のメニューは行を分ける(13.2)のに、買い物の品物は分けない。この違いの理由。

| | 何のために記録するか | 必要な細かさ |
|---|---|---|
| 食事のメニュー | 安定した食事がとれているかを見る(4.2) | 1品ずつ |
| 買い物の品物 | 無駄なく抑えられているかを見る(4.2) | 期間ごとの合計で足りる |

**目的に対して必要な細かさが違う。** これが行を分けるかどうかの判断基準になっている。（判断の記録 #14）

**文章で持つことは、行を分けることの劣化版ではない**

備考欄に「鶏むね肉、キャベツ、米5kg」と書いてあれば、本当に品物ごとの集計がしたくなったとき、その文章から拾える。最初から入力しなければデータは存在しない。つまり**判断を先送りできる形**であり、11.3「最小限を作ってから足す」と一致する。

**書き方に決まりは作らない**

決まりを作ると入力の手間が増え、続かなくなる。代わりに、入力欄に例を薄く表示して書き方を思い出させるだけにする(例:「米5kg、鶏むね肉、調味料」)。強制しないので手間は増えない。

### 13.7 この設計に付いている名前

面接で聞かれたとき用。中身は上で説明したとおり。

| 名前 | 中身 |
|---|---|
| 正規化 | 1つのマスに1つの値だけ入れる。同じ値を2か所に書かない |
| 第1正規形 | 1マス1値。メニューを別の表にしたのがこれ |
| 具象クラス継承 | 種類ごとに完全に別の表にする形 |
| 単一テーブル継承 | 1つの表に全部入れる形 |
| **クラステーブル継承** | **共通の表+種類ごとの表。採用したもの** |
| ポリモーフィック関連 | 子の表が「どの表を参照しているか」を列に持つ形。参照先が複数になり、整合性を保証できなくなるためアンチパターンとされる。**この設計では、参照先が常に記録の表1つなので該当しない** |

### 13.8 通知の送り先を保存する表

**4つ目の表を足す。**

#### なぜ必要なのか

通知は「このアプリに送る」という形では送れない。**「この端末のこのブラウザに送る」**という形でしか送れない。

```
1. アプリを開いて「通知を許可」を押す
       ↓
2. その瞬間、この端末専用の送り先が1つ発行される
       ↓
3. その送り先を保存しておく        ← この表が要る
       ↓
4. 毎晩21時、保存した送り先に向けて通知を送る
```

送り先はこういう長い文字列である。

```
https://web.push.apple.com/QHxGf9kZ...(以下100文字ほど続く)
```

**自分で決められない。** 2番の瞬間に自動で発行されるもので、端末ごとに違う。保存しないと、4番の時点で送り先が分からなくなる。

> 記録の表に列を足す形は採らない。送り先は日付とも食事とも関係がなく、記録1件ごとに送り先が入る形になり意味が合わないため（判断の記録 #52）

#### この表が使われる場面

| 場面 | この表に対して何をするか | 頻度 |
|---|---|---|
| 通知を許可した | 1行足す | 端末ごとに1回 |
| **毎晩21時** | **全部読む** | **毎日。これが主な用途** |
| 送信に失敗した | その行を消す | たまに |
| 通知を切った | その行を消す | ごくたまに |

**書き込みはほとんど起きない。ほぼ読むだけの表である。**

#### 表の形

```
送り先の表
  id       番号
  利用者   誰の端末か。7.9 のアクセス制御がこの列を使う
  送り先   通知の送り先。重複できない
  登録日時 いつ登録したか
```

**4列だけ。**

| 入れないもの | 理由 |
|---|---|
| 端末の名前 | 全部の送り先に送るので区別が要らない（判断の記録 #53） |
| オンかオフか | 通知を切ったら行を消すので不要（判断の記録 #55） |
| 最後に送れた日時 | 送信に失敗したら消すので、残っている行は有効（判断の記録 #54） |

※ 利用者の列は、当初「記録の表と揃えて後から足す」としていた（判断の記録 #56）。7.9 でログインを作ることになり、記録の表と揃えて**最初から置く**ことになった。揃えるという方針は変えていない。

#### 動き方

| 項目 | 決めたこと |
|---|---|
| 複数の端末 | **登録されている送り先、全部に送る** |
| 古い送り先 | **送信に失敗したら、その行を消す。** 送り先が有効かどうかは送ってみないと分からないため、これが唯一確実な方法 |
| 通知を切ったとき | **行を消す** |
| 同じ送り先が2回登録されたら | **重複できない決まりにする。** 同じものが来たら登録日時だけ更新する |

#### 9.1 の検証結果

**既存の3つの表には一切手を触れていない。表を1つ足すだけで済んだ。**

9.1 の「今あるデータの構造を壊さずに、新しいものを追加できること」が、最初の実例で満たされた。

**ただし今回は条件が易しい例である。** 送り先は記録と全く関係がないため、ぶつかりようがなかった。本当の試練は、将来「起床・就寝時刻」や「掃除した場所」を足すとき(8.2)。あれは記録の仲間なので、13.5 の共通の表に乗るかどうかが問われる。

## 14. 使う技術

| 選ぶ対象 | 決定 |
|---|---|
| 作る形 | **ホーム画面に追加して使うWebアプリ** |
| データの保管場所 | **Supabase** |
| 定時実行 | **Supabase Cron**(pg_cron) |
| 通知の送信処理の置き場所 | **Supabase の Edge Function** |
| ログインとアクセス制御 | **Supabase Auth + 行単位のアクセス制御**(7.9) |
| 画面を作る道具 | **React + Vite** |
| ホーム画面への追加と通知の受け取り | **vite-plugin-pwa**(injectManifest 方式) |
| 公開する場所 | **Vercel** |
| グラフを描く部品 | **未決定。** グラフを作る段階で決める |

> 選んだ理由と、選ばなかった候補は『判断の記録.md』#36〜#51 にある。

### 14.1 構成

```
iPhone のホーム画面
    │ 開く
    ↓
Webアプリ（React + Vite、Vercel に置く）
    │ 読み書き
    ↓
Supabase（記録の表・食事の表・メニューの表・送り先の表）
    ↑ 読む
Supabase Cron（毎晩21時に動く）
    │ 呼ぶ
    ↓
Edge Function（通知の文章を作って送る）
    │
    ↓
iPhone に通知が届く
```

### 14.2 通知の仕組みに必要なもの

**1. 鍵のペア**

公開鍵と秘密鍵という、対になった2つのデータを自分で生成する(VAPID鍵と呼ばれる)。

- 公開鍵: アプリ側に渡す。「この送り主からの通知を受け取る」という紐付けに使う
- 秘密鍵: サーバー側に置く。送信するとき、送り主が本物だと証明するために使う

**2. 送り先の情報**

13.8 の表に保存する。

**3. 送信する処理**

決まった時刻に動いて、次を行う。

1. データベースから、その日の記録の状況を読む(枠が埋まっているか)
2. 通知の文章を作る
3. 秘密鍵で署名を作る
4. 保存してある送り先に向けて送る

実際に送る部分は既にある部品(web-push というライブラリ)を使える。暗号の処理をゼロから書く必要はない。

### 14.3 承知した上で受け入れる制約

**1. 通知が止まる可能性がある**

iPhone でのWebアプリの通知は、最初は動くが、その後予期せず止まる場合があるという報告が開発者から出ている。

**対処:通知は補助とし、開いた瞬間の画面を本体とする。** 12.5 で「最初に出るのは今日の画面」と決めているので、その方針で一貫している。（判断の記録 #39、#46）

**2. 7日使わないとプロジェクトが止まる**

Supabase の無料プランは、7日間データベースへのアクセスがないとプロジェクトが一時停止する。

| 項目 | 内容 |
|---|---|
| 停止を防ぐ条件 | 毎日数回のアクセスがあれば防げる。10.3 の目標通りに使っていれば発生しない |
| 復元 | 管理画面から「Resume project」で再開できる。**データや設定は以前の状態に戻る** |
| 復元できる期間 | 停止してから1年以内 |
| **起きる不便** | **7日あけてアプリを開いた瞬間は、記録が保存できない。** 管理画面を開いて再開させてから、もう一度アプリを開くことになる |

停止中は定時実行も止まるため、**記録が途切れたときには通知も止まる。** これを承知した上で、上の「通知は補助」の方針で受け入れる。（判断の記録 #46）

**3. 試作用と本番用のプロジェクトを分けられない**

無料プランは同じ組織で2つまで。my-task-app のプロジェクトを残すため、新しいアプリが2つ目になり枠が埋まる。試作も本番も同じプロジェクトで行う。

記録を始めるのは試作が終わってからなので、試作中に消して困るデータはまだ存在しない。（判断の記録 #47）

**4. Vercel の無料プランは商用利用が禁止**

ポートフォリオと自分用なので該当しない。将来お金を取る形にするなら、有料プランか Cloudflare Pages への移動が要る。（判断の記録 #51）
